# Research: 高级动态服务界面\n\n**Date**: 2026-10-17\n**Feature**: [spec.md](spec.md)\n\n## Existing implementation findings\n\n- The active path is `AgentResult.ui_proposal` → `ConversationService.publish_ui_projection` → `validate_components` → persisted versioned `UIDocument` → React `UIDocumentRenderer`. Existing GET/refresh/action routes are in `backend/serviceos_api/api/business.py`; no new route is required for a richer projection.\n- `ui_proposal` currently has required `purpose`, `audience`, `fallback_text`, `component_hints`; optional `options`, `knowledge_source_id`, and `case_id`. Its parser rejects unknown fields and bounds strings, options, audience, and component names (`backend/serviceos_api/agents/result.py`).\n- The prompt and parser allow `DiagnosticSteps`, `RiskNotice`, and `HandoffSummary`, but the Agent projection path only handles question cards and the metric chart for customers, and `CaseProcessFlow` for staff. The rendered Catalog instead has `RiskAlert`, exposing a contract mismatch. `fallback_text` is accepted and checked, but projection publication currently emits a fixed fallback.\n- Existing `UIDocument`, `UIActionInvocation`, revision/expiry behavior, SSE event path, and application services already provide a foundation for safe dynamic projections and typed interactions. New business tables should not be added unless an explicit new durable user choice/state is required.\n- Current UI contract fields are broad (`type: str`, `props: dict[str, str]`); Python Catalog metadata and the frontend renderer catalog are separately maintained. A typed/versioned catalog contract and parity checks should reduce silent drift.\n- Existing visualization tests cover fixed source-bound chart data and server-derived Case flow. Current project documentation records no real-provider decision-quality evaluation and skipped PostgreSQL projection acceptance when the disposable test database was unavailable.\n\n## External references and decisions\n\n### Decision: Keep a declarative, catalog-bound UI; do not render model-generated code\n\n**Rationale**: The product already has a fixed host application and domain-specific security rules. The Agent should choose a purpose and allowed component composition; the application retains ownership of rendering, access control, business values, and action execution. A2UI similarly models declarative component catalogs and transports messages rather than executable interface code; its v1.0 protocol specifies catalog resolution and accessibility attributes. [A2UI v1.0 protocol](https://github.com/a2ui-project/a2ui/blob/main/specification/v1_0/docs/a2ui_protocol.md), [Google A2UI overview](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/)\n\n**Alternatives considered**:\n- Let the model generate arbitrary HTML/SVG: rejected because it bypasses the existing renderer/catalog trust boundary and makes permission, accessibility, and content validation harder.\n- Adopt a general remote iframe application model: rejected for this in-repo `/support` and `/desk` product slice; it adds a separate host/security/runtime model where the current React renderer already exists.\n- Keep the current hint list unchanged and add more prompt instructions: rejected because the current code already shows that prompt/parser/component support can drift apart.\n\n### Decision: Treat every UI action as a typed, separately authorized application intent\n\n**Rationale**: A proposal must not become business authority. Existing UI actions already pass through application services and check actor, active document revision, payload, and idempotency. A2UI separates declarative UI data from renderer actions; continue this project’s stricter server-owned action model rather than allowing proposal-supplied endpoints or arbitrary tool names. [A2UI protocol](https://github.com/a2ui-project/a2ui/blob/main/specification/v1_0/docs/a2ui_protocol.md)\n\n### Decision: Design each card as one focused service task, with text fallback\n\n**Rationale**: Customer cards should help with one step, such as identifying a product, submitting evidence, or answering a diagnostic question. Keep the conversation as the continuous fallback. OpenAI UI guidance recommends inline cards for quick single-purpose interactions and cautions against nested navigation and nested scrolling. [OpenAI UI guidelines](https://developers.openai.com/plugins/concepts/ui-guidelines)\n\n### Decision: Make visual and interactive content accessible without color or pointer-only affordances\n\n**Rationale**: Forms need associated labels and instructions; form errors require text feedback. Chart summaries and underlying data should also be available in text. [W3C WAI form labels](https://www.w3.org/WAI/tutorials/forms/labels/), [W3C WAI form validation](https://www.w3.org/WAI/tutorials/forms/validation/), [W3C WAI tables](https://www.w3.org/WAI/tutorials/tables/)\n\n## Technical decisions for planning\n\n1. Extend current contracts and projection in place; preserve ConversationService as the publication authority and application services as the only write path.\n2. Define one explicit versioned proposal schema and one typed component catalog. Keep server-side data resolvers for Case, Task, Device/verified facts, knowledge metrics, and evidence states.\n3. Use existing `RichReply` alert/steps blocks for message-scoped safety and diagnostic guidance, existing question/evidence services for customer input, and `UIDocument` for refreshable durable progress. Add no parallel component/action protocol where one already exists.\n4. Use existing UIDocument revision/expiry and action idempotency; do not persist model-generated UI trees as business facts or add a second state machine.\n5. Validate each component server-side and again in the React renderer. Keep unknown/unsupported content on the text path.\n6. Evaluate model choice quality separately from deterministic projection/rendering correctness; live-provider tests remain gated on configured, approved provider access.\n\n## Known assumptions and unresolved external conditions\n\n- The user has authorized planning a premium dynamic service experience based on the previously discussed direction; no new page, paid resource, provider, or third-party UI runtime is authorized by this plan.\n- The user-supplied S1 Pro/T8D04 knowledge source still needs current accuracy and usage-right approval before broader public use; its workbook publication labels are not external verification.\n- No real Provider credential was used for this research. No provider-quality claim is made.\n
