# Feature Specification: 高级动态服务界面\n\n**Feature Branch**: `016-dynamic-service-interface`\n**Created**: 2026-10-17\n**Status**: Implemented; local automated validation complete; provider and production acceptance pending\n**Input**: User request: “我希望把这个做好，做高级。请你参考相关资料，基于实际代码给我回答；还有是高级感的动态服务界面。按你的建议使用计划skill稳步开发。”\n\n## User Scenarios & Testing\n\n### User Story 1 - 客户获得恰当的动态服务引导 (Priority: P1)\n\n客户描述设备问题后，服务界面根据当前证据缺口、已核验设备身份和风险，展示清晰、精致且可操作的下一步，例如安全提示、选项澄清、证据清单或分步排查。客户可继续使用普通文字消息完成服务。\n\n**Why this priority**: 客户侧是动态服务界面的主要入口；首要价值是减少重复描述，让客户理解现在要做什么以及为什么。\n\n**Independent Test**: 使用一组包含型号不明、证据不足、危险信号和常见排障的代表性场景，验证界面只呈现当前适用的下一步，选项回答能回到同一服务上下文，且纯文字路径仍可完成。\n\n**Acceptance Scenarios**:\n\n1. **Given** 设备型号或症状仍有多种可能，**When** Agent 建议澄清，**Then** 客户看到简明选项卡，并可用普通文字回答。\n2. **Given** 证据不足且当前没有优先安全风险，**When** 服务需要补充材料，**Then** 客户看到有目的说明的证据清单或受支持的上传入口，且清单状态来自真实记录。\n3. **Given** 当前信息指向安全风险，**When** 服务界面生成本轮引导，**Then** 安全提示先于普通排障步骤显示，并清楚说明停止条件与求助方式。\n4. **Given** 客户不使用动态卡片或卡片无法加载，**When** 继续服务，**Then** 客户仍能通过文字消息完成必要交互，不丢失已提交内容。\n\n### User Story 2 - 客户看见可信的服务进度 (Priority: P1)\n\n客户能在会话中理解目前服务处于哪一步、正在等谁提供什么，以及哪些结果尚未核验；视觉进度不会把模型推测、Worker 生命周期或模拟回执伪装成已解决事实。\n\n**Why this priority**: 清楚的等待原因与下一步能降低不确定感；错误显示完成状态会损害信任并影响售后决策。\n\n**Independent Test**: 以真实 Case、Task、Mock Action 和 Verification 状态组合验证进度说明；逐项修改持久业务状态，检查展示更新、权限过滤和文字降级。\n\n**Acceptance Scenarios**:\n\n1. **Given** Case 正等待客户补充资料，**When** 客户查看服务界面，**Then** 页面说明等待对象与待补信息，不显示“已解决”。\n2. **Given** 模拟售后动作已经成功但客户结果尚未确认，**When** 客户查看进度，**Then** 动作回执与解决核验分别表达，不把动作成功等同于 Case 已解决。\n3. **Given** 业务状态或 UI revision 已变化，**When** 客户打开旧界面，**Then** 系统刷新或安全降级，旧交互不能提交过期操作。\n\n### User Story 3 - 客服获得可审查的动态工作视图 (Priority: P2)\n\n客服看到基于授权 Case、证据、人工任务和动作记录生成的重点摘要、来源和流程关系，可以快速判断下一步；客户私密信息与内部备注不会进入客户界面。\n\n**Why this priority**: 客服需要比客户更完整的上下文，但展示必须保持来源清晰、业务事实与 Agent 假设分离。\n\n**Independent Test**: 使用同一会话的客户/客服身份分别读取动态界面，确认客服视图可追溯到授权业务记录且客户响应中不存在内部内容。\n\n**Acceptance Scenarios**:\n\n1. **Given** 当前会话关联 Case 与人工任务，**When** 客服查看动态工作视图，**Then** 摘要和流程状态能回到对应资源及版本。\n2. **Given** 模型建议与已核验业务记录冲突，**When** 客服查看视图，**Then** 业务记录优先，建议标为待核验或不展示。\n3. **Given** 客户请求协助或客服执行受控操作，**When** 从视图触发交互，**Then** 后端按已授权类型重新验证权限、资源版本、策略和幂等要求。\n\n### Edge Cases\n\n- 设备型号未核验、设备与 Case 未关联、知识来源未知或已变更时，不渲染依赖该来源的专属图解。\n- UI 提案字段未知、组件不支持、内容超限、结构校验失败或 audience 不匹配时，保留普通回复并降级。\n- 当前资源版本过期、客户刷新或 SSE 重连后，旧组件不得复用过期数据或重放写操作。\n- 无 Provider、Agent 失败、超时、重复问题、并行诊断任务或没有可用业务卡片时，界面显示真实状态或普通文字，不显示虚假加载完成。\n- 屏幕阅读器、键盘、窄屏、放大文本和高对比度设置下，关键内容、图表数值和控件仍可理解与操作。\n- 估算图表的用户资料来源虽标记 Published/Visible，但现行准确性或使用权未确认时，不对客户展示。\n\n## Requirements\n\n### Functional Requirements\n\n- **FR-001**: 系统 MUST 按客户/客服角色、会话协作模式、授权上下文和当前服务阶段，选择适当的动态服务界面；无合适界面时使用普通文字体验。\n- **FR-002**: 系统 MUST 将安全提示、证据收集、问题澄清、分步排查、状态说明和图解区分为有明确用途的界面内容；高风险提示 MUST 优先于一般排障。\n- **FR-003**: 系统 MUST 只展示有授权来源的事实、状态和估算；模型建议不得写成已核验设备事实、成功业务动作或 Case 解决结论。\n- **FR-004**: 系统 MUST 为每个动态内容提供清楚的标题、下一步说明和适用条件；面向客户的图表 MUST 显示来源、单位、估算性质及可读的等价文本数据。\n- **FR-005**: 系统 MUST 支持适配桌面与移动设备的界面；主要交互须可键盘操作，表单控件有可识别标签，提交、成功、失败、等待与重试状态清楚可见。\n- **FR-006**: 系统 MUST 为不支持、无权限、过期、校验失败或无法获取来源数据的动态内容提供安全文字降级，且继续保留普通消息服务。\n- **FR-007**: 系统 MUST 将客户公开内容与客服内部内容隔离；客服流程视图只能引用当前用户已授权且与会话关联的资源。\n- **FR-008**: 系统 MUST 将界面交互限制为已批准的类型化业务意图；提交时继续经过现有应用服务的身份、权限、版本、状态和幂等验证。\n- **FR-009**: 系统 MUST 使图表与流程状态来自可信来源或持久业务记录；模型不得自行提交可被解释为真实业务状态的数值、节点状态、回执或解决结论。\n- **FR-010**: 系统 MUST 为重复追问、建议卡选择、无卡片回退、过期恢复、越权拒绝和服务结果核验提供可观察的验收路径。\n\n### Key Entities\n\n- **界面意图**：Agent 提出的服务目标、受众和内容类型建议；不代表业务事实或执行权限。\n- **动态服务文档**：针对当前对话/Case 生成的受版本管理的界面投影，包含受信组件、数据来源和降级文本。\n- **业务证据与来源**：用户陈述、已核验 Device Passport 事实、知识条目及可追溯服务记录；不同可信等级不可混同。\n- **服务交互**：客户回答、证据提交或受控 UI action；提交后通过既有业务服务记录并接受服务端授权。\n\n## Success Criteria\n\n### Measurable Outcomes\n\n- **SC-001**: 在至少 20 个覆盖安全、型号澄清、证据收集、排障、客服协作、核验及失败回退的验收场景中，所有展示的事实、状态、来源和动作均符合角色授权与业务记录；不得出现越权或虚报完成。\n- **SC-002**: 在代表性客户任务评测中，至少 90% 的参与者能在首次界面引导下完成当前需要的澄清或证据补充；无法完成时能找到普通文字路径或人工协助入口。\n- **SC-003**: 关键页面在 390px 手机宽度与 1280px 桌面宽度下均无横向溢出；动态卡片的关键文本、状态、来源和控件可通过键盘与屏幕阅读器识别。\n- **SC-004**: 对于所有已实现动态组件，未知组件、无权来源、过期 revision 或不匹配业务状态均能拒绝、隐藏或安全降级，且不执行写操作。\n- **SC-005**: 用户在模型不可用、提案无效或动态界面不兼容时仍可继续文字服务；提交中的真实业务动作不会因刷新自动重复执行。\n\n## Assumptions\n\n- 本特性扩展当前 `/support` 与 `/desk` 的受控动态 UI，不新增独立产品入口，不采用任意 HTML/JavaScript/SVG 代码生成。\n- 第一阶段优先完善已有 UI Proposal、UIDocument、Catalog Validator 与 Renderer，并交付安全提示、证据引导、问题澄清、分步排查和可信进度的最小闭环。\n- 当前模拟售后动作仍明确标记为 Mock；生产身份源、真实 Anker 操作和未确认的外部知识使用权不在本特性中自动启用。\n- UI 仍是可失效投影；Conversation、Service Case、Device Passport、Service Task、Agent Run 和业务回执继续独立建模。\n- 质量目标以真实场景与人工评测验证；测试夹具、浏览器快照或模型自评不能单独证明真实 Provider 的选择质量。\n
