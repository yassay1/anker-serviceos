# Data Model: 高级动态服务界面\n\nThis feature primarily extends existing UI projection entities; it does not merge them with business records.\n\n## Existing entities reused\n\n### UI Proposal\n\nInternal AgentRun result describing a proposed service purpose, audience, bounded content blocks, and optional bounded choices or allowlisted source references.\n\n- **Trust**: untrusted model output until strict parsing and application-level projection.\n- **Lifecycle**: proposal → validated projection or text fallback; it is not independently published or executable.\n- **Rules**: typed/versioned; no arbitrary HTML, JavaScript, URL, API endpoint, direct business status, device fact, or action permission.\n\n### UIDocument\n\nVersioned view for a conversation and audience, persisted through ConversationService.\n\n- **Existing attributes**: stable UI identity, revision, schema/catalog version, surface, audience, visibility, source AgentRun, component list, fallback, status, expiry, and context signature.\n- **Lifecycle**: active document may be superseded by a newer revision; stale/expired content is refreshed or safely rendered as fallback.\n- **Rules**: PUBLIC for customer audience and INTERNAL for staff; current resource references and versions must be authorized.\n\n### UIComponent\n\nOne renderer-supported component inside a UIDocument.\n\n- **Existing structure**: ID, catalog type, typed-by-catalog props, authorized data source/binding/version, zero or more registered actions, children, and optional chart/flow payload.\n- **Rules**: component type and fields must match the active catalog; one component cannot carry mismatched chart/flow/action payloads.\n- **Planned additions**: only add a component schema when neither bounded `RichReply` blocks nor existing Case Evidence/diagnostic UI can serve the intent. The current target is a customer-safe progress projection from authorized linked Case/task records; safety notices and ordered guidance remain message-attached `RichReply` blocks.\n\n### UIActionInvocation\n\nAudit/idempotency record for a user action invoked from a UI document.\n\n- **Existing attributes**: actor and tenant identity, source document, client action ID, request fingerprint, and outcome metadata.\n- **Rules**: action is only a typed intent routed through an existing application service; duplicate keys are idempotent, conflicting reuse is rejected, and stale document/resource versions cannot write.\n\n## Existing business sources (read-only projections)\n\n### Device Passport and Device Fact\n\nLong-lived device identity and facts; only verified, applicable facts may appear as verified in the customer UI. Candidate/claimed/model-inferred facts remain labeled as such or are omitted.\n\n### Service Case, Service Task, Evidence, Action, Verification, and Follow-up\n\nPersistent records that provide current progress and next-step context. A mock action receipt is explicitly labeled Mock; only the existing verification service can determine the verified resolution state.\n\n### Knowledge entry\n\nCurated source with identity, content/version fingerprint, model applicability, publication/visibility metadata, and rights/review status. Model output identifies at most an allowlisted source; the resolver controls values and audience.\n\n## Relationships\n\n```text\nAgentRun ──proposes──> UI Proposal ──validated/projected by──> UIDocument\nConversation ──owns versions of──> UIDocument ──contains──> UIComponent\nUIComponent ──binds to authorized version of──> Business Source\nUIComponent ──may expose registered intent──> UIActionInvocation ──routes to──> Application Service\nApplication Service ──reads/writes──> Case / Device / Task / Evidence / Action / Verification\n```\n\nNo direct proposal-to-business-state write relationship is introduced.\n
