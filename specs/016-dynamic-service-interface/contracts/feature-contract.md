# 高级动态服务界面 · Feature Contract\n\n## Purpose and scope\n\nEvolve the current Agent → UIDocument → Catalog Validator → React Renderer path into a coherent, polished, task-focused after-sales interface for `/support` and `/desk`.\n\nThe feature is an additive extension of the current internal proposal and UIDocument contracts. It does not introduce arbitrary code rendering, new business authority, a new conversation/case/device relationship, or a new external integration.\n\n## Proposal boundary\n\nThe model may propose a service goal, intended audience, and one or more supported content kinds with bounded user-facing text/options and allowlisted source IDs. It MUST NOT provide:\n\n- HTML, JavaScript, CSS, SVG, arbitrary URLs, executable expressions, SQL, or API routes;\n- values or states presented as verified facts without an authoritative source;\n- arbitrary resource IDs, authorization decisions, business status, external receipts, or resolution decisions;\n- unregistered write actions or action endpoint parameters.\n\nParser-valid hints that are not implemented by the current projection are not considered supported. Prompt, Pydantic/parser, backend component catalog, OpenAPI, and renderer must describe the same active component set. Optional fields must have defined behavior; `fallback_text` must either be consumed by the published document or removed in a versioned contract update.\n\n## Component intents\n\nUse the two existing bounded presentation paths according to their lifecycle: `RichReply` carries content attached to a particular Agent message; `UIDocument` carries a versioned, refreshable projection of current authorized business state and registered interactions. Do not duplicate the same component or action in both paths. Proposal shape v1 remains strict and is covered by the enclosing AgentRun result schema version; published components are versioned by UIDocument `schema_version` and `catalog_version`.\n\nThe initial target set covers these single-purpose service intents:\n\n- Safety notice and stopping conditions as a bounded `RichReply` alert; server/rule policy may require it and it must precede ordinary troubleshooting.\n- Ordered diagnostic guidance as a bounded `RichReply` steps block; steps remain guidance, not proof of completion.\n- Clarification question with 2–5 bounded choices or a labeled free-text answer in `UIDocument`, bound to the active diagnostic question revision.\n- Evidence request/status through existing `RichReply` action links and Case Evidence UI; upload/check state remains from existing evidence services.\n- Customer-safe service progress and explanation of who/what is awaited in `UIDocument`, derived from the currently linked Case/task records.\n- Customer knowledge estimate chart with visible source/applicability/unit/estimate language and equivalent text values.\n- Staff-only process flow from current authorized Case, Task, Mock Action, Follow-up, and Verification records.\n\nThe first implementation stage may deliver a subset as a complete vertical slice; every advertised component must be implemented or explicitly marked unsupported.\n\n## Audience, source, and action rules\n\n- Customer documents are PUBLIC and may use only the current conversation, an authorized linked Case/task projection, AgentRun, evidence, verified device, and approved knowledge sources.\n- Staff documents are INTERNAL and may use only resources authorized for the staff actor and currently linked to the conversation/Case.\n- Every source binding includes resource identity and version; stale versions refresh or fall back safely.\n- Model suggestions remain hypotheses. Only persistent business records and verified knowledge adapters provide authoritative statuses and values.\n- Components have no actions by default. Interactive components reference a finite registered intent and schema; the backend revalidates actor, tenant, resource linkage, current policy, revision/version, and idempotency before application-service execution.\n- Case status becomes RESOLVED only through the current result-verification rules. A successful Mock receipt alone is not a resolution.\n\n## Publication and compatibility\n\n- Reuse `GET /api/v1/conversations/{id}/ui-document`, `POST /api/v1/conversations/{id}/ui-document/refresh`, and `POST /api/v1/conversations/{id}/ui-actions` unless an acceptance scenario proves a contract gap.\n- Preserve UIDocument revisioning, expiry, current publication guard, PUBLIC/INTERNAL filtering, and server-side fallback.\n- Version the proposal/catalog changes. Older supported documents may continue rendering; unknown component versions or types do not run actions and fall back to text.\n- Generate frontend API types from actual OpenAPI. Runtime Catalog metadata and React renderer registration must have parity checks.\n\n## Accessibility and presentation\n\n- Each card has one clear purpose and compact visual hierarchy, consistent with the current brand surfaces.\n- Safety and state are conveyed by text/labels as well as color.\n- Every interactive field has an associated label/instructions; submit/error/success/wait/retry states are announced and recoverable.\n- Charts include a concise textual summary and equivalent values; SVG is not the only access path.\n- Keyboard and screen reader users can complete the same supported interactions as pointer users; mobile layouts have no horizontal overflow.\n\n## Acceptance boundary\n\nValidate successful/failed projection and rendering, role/source restrictions, stale versions, no-provider/text-only fallback, safety ordering, repeat-question suppression, source provenance, accessibility, mobile/desktop states, typed action authorization/idempotency, and verified resolution invariants. Live provider selection quality is a separate evaluation gate and must not be claimed from fixtures alone.\n
