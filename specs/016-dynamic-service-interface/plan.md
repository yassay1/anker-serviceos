# Implementation Plan: 高级动态服务界面\n\n**Branch**: `016-dynamic-service-interface` | **Date**: 2026-10-17 | **Spec**: [spec.md](spec.md)\n\n## Summary\n\n把现有受控 UI 投影升级为面向售后任务的动态服务界面：Agent 只提出界面意图，服务端依据已授权来源生成安全提示、澄清问题、证据引导、诊断步骤和真实进度；前端以现有 React Catalog 渲染。沿用 ConversationService、UIDocument revision/expiry、应用服务写入、SSE 与普通消息回退。先修正现有 proposal/Catalog/Renderer 不一致，再按完整业务纵切面逐类交付，不引入任意代码执行或第二套业务状态。\n\n## Technical Context\n\n**Language/Version**: Python 3.12；TypeScript/React on Node 24\n**Primary Dependencies**: 现有 FastAPI、Pydantic、SQLAlchemy、React、Vite、生成式 OpenAPI Client；不计划新增 UI runtime 或图表依赖\n**Storage**: 现有 PostgreSQL `serviceos` 业务 Schema；UIDocument 与 UIActionInvocation 已持久化。默认不新增业务表或迁移\n**Testing**: 后端 pytest（纯单元及隔离 PostgreSQL）；OpenAPI export/check；前端 API parity、typecheck/build、Playwright browser/live scenarios\n**Target Platform**: 当前单一 Web 应用 `/support` 与 `/desk`，桌面和移动浏览器\n**Project Type**: 前后端分离的模块化单体 + 独立 Worker\n**Performance Goals**: 不把模型调用放进用户 HTTP 等待；沿用已记录的消息受理 P95 <500ms 目标。动态投影、Renderer、fallback 的时延应分别采集并以当前基线对比，不用虚构阈值\n**Constraints**: Agent UI 只能声明式引用受信组件；业务事实来自授权持久记录或经批准来源；公开发布经 ConversationService；动作经现有应用服务鉴权/版本/幂等；内部内容严格隔离；支持文字回退和移动端/无障碍交互\n**Scale/Scope**: 首个目标是 `/support` 与 `/desk` 的完整售后服务纵切面；组件数量按可验证用户任务增长，不建设通用网页生成器\n\n## Constitution Check\n\n| Principle / gate | Assessment |\n|---|---|\n| I. It does not carry component execution code, arbitrary props, direct business states, endpoint URLs, or unsupervised actions.\n2. **One contract across producer and renderer.** Align the Agent prompt/TypedDict/Pydantic parser, server Catalog Validator, OpenAPI UIDocument contract, and React renderer registration. Prefer typed component variants and generated/shared contract checks over separately drifting name lists.\n3. **Server owns materialization.** Server adapters resolve verified device facts, evidence inspection state, Case/Task/Action/Verification state and approved knowledge data. The UI proposal may request a visualization but cannot invent its numeric or status payload.\n4. **One registered intent per interaction.** A component can expose only a named action schema already supported by the application. The backend rechecks actor, tenant, source links, current state/revision, policy and idempotency. Model-generated route/action strings are forbidden.\n5. **Progressive enhancement.** Every component has meaningful text fallback, loading/empty/failed/expired states, keyboard/screen-reader semantics and responsive layout. If projection fails, the message and normal conversation remain usable.\n6. **Evidence provenance.** Add a same-AgentRun source-use check for knowledge chart proposals, or revise the prompt/product contract before launch. Curated source current accuracy/rights must be approved separately; Published/Visible labels alone are insufficient.\n\n## Planned delivery slices\n\n### Slice 1 — Contract integrity and premium interaction foundation\n\n- Resolve unsupported proposal hints (`DiagnosticSteps`, `RiskNotice`, `HandoffSummary`) and the `RiskAlert` naming discrepancy. Keep per-message safety/diagnostic blocks in the existing bounded `RichReply`; keep persistent task/progress projections in `UIDocument`.\n- Decide and implement actual `fallback_text` behavior; avoid a field that passes validation but has no effect.\n- Introduce the versioned component contract and catalog/renderer parity tests.\n- Refine card hierarchy, status language, responsive behavior, semantic labels and submit/error/wait/fallback feedback in current design tokens.\n- Acceptance: supported and unsupported proposals have deterministic projection behavior; stale/unknown/invalid proposal safely becomes text; no business writes result from proposal alone.\n\n### Slice 2 — Customer guided service vertical slice\n\n- Provide risk-first safety notices and ordered diagnostic guidance through existing bounded `RichReply` blocks; provide clarification and current evidence state through existing `UIDocument`, diagnostic and Case Evidence paths.\n- Order high-risk safety information ahead of general diagnosis; show explicit stop conditions and human-help path.\n- Bind evidence status and diagnostic question lifecycle to existing Case/evidence/diagnostic services. Suppress answered/expired/repeated questions; do not create parallel upload or diagnostic action protocols.\n- Acceptance: representative scenarios from ambiguous model through safe evidence collection and one diagnostic step complete on both card and plain-text paths; no claims unsupported by evidence.\n\n### Slice 3 — Trusted progress and staff work view\n\n- Extend customer-safe progress and staff-only Case process visualization from persisted current records.\n- Clearly separate Case, human task, mock action receipt, customer confirmation and verification status.\n- Check resource freshness, linked Case permissions and PUBLIC/INTERNAL filtering on every projection.\n- Acceptance: action success cannot render as resolved without verified customer confirmation; customers cannot observe internal tasks/notes; staff nodes link to authorized sources.\n\n### Slice 4 — Quality, accessibility and evaluation\n\n- Complete screen-reader/keyboard, chart text equivalent, responsive, reduced-motion, loading/error/empty state and interaction feedback review.\n- Record deterministic projection/render/fallback/stale-rejection checks. Build a representative service scenario set and human evaluation rubric for component appropriateness and clarity.\n- Run PostgreSQL-backed integration only against a disposable local database. Evaluate live-provider quality only if an approved provider is configured; report separately from fixtures.\n- Acceptance: measurable outcomes in spec are met or remain explicitly gated with evidence and reason.\n\n## Current source tree\n\n```text\nbackend/serviceos_api/agents/result.py             # Agent result and ui_proposal validation\nbackend/serviceos_api/agents/runtime.py            # Agent system prompt and typed runtime output\nbackend/serviceos_api/application/contracts.py      # API/UI data contracts\nbackend/serviceos_api/application/ui_catalog.py     # Server-side component and source validation\nbackend/serviceos_api/application/ui_visualizations.py # Server-owned charts and Case flow projection\nbackend/serviceos_api/application/services.py       # ConversationService publication and UI actions\nbackend/serviceos_api/api/business.py               # Existing UI document/action routes\nbackend/serviceos_api/persistence/models.py         # Existing UIDocument and UIActionInvocation\nbackend/tests/                                      # Agent, Catalog, visualization and DB regressions\nfrontend/src/features/ui-document/                   # Catalog validation and React Renderer\nfrontend/src/styles/                                 # Shared and product UI tokens/surfaces\nfrontend/tests/                                      # Browser interaction/accessibility regressions\ncontracts/openapi.json                               # Exported actual API contract\n```\n\n## Risks and mitigations\n\n- **Catalog drift**: require exact parity between prompt/parser, backend Catalog, OpenAPI and frontend; reject unsupported proposal types safely.\n- **Misleading or stale progress**: derive status only from durable business records and bind source versions; keep verification separate from actions.\n- **Prompt injection/model hallucination**: proposal is untrusted, server resolves data, validates audience/resource/version and controls public publication.\n- **Static curated data treated as current policy**: require source ownership/currentness/rights approval before enabling the metric to customers.\n- **Premium appearance hides weak interaction**: acceptance measures task completion, labels, keyboard accessibility, failure recovery and text fallback alongside visual consistency.\n- **Real-provider dependency**: never mark quality/latency met from controlled fixtures; retain explicit Provider acceptance gate.\n\n## Project Structure Decision\n\nUse the existing single Web app and modular backend boundaries. No new project, service, database, production provider, cloud resource, or third-party renderer is introduced.
