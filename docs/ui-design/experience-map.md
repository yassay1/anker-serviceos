# 售后通全局体验与交互地图

状态：设计基线草案  
依据：V1 产品与领域定义、当前 OpenAPI、用户提供的界面参考图。

## 1. 页面地图

### 客户空间

```text
客户空间
├─ 服务入口
│  └─ 一个主按钮「进入对话」→ 服务工作区
│     ├─ 对话：当前 Conversation 与受控交互卡
│     ├─ 历史对话：Conversation 列表
│     ├─ 服务记录：Service Case 列表
│     ├─ 服务详情：当前 Case、阶段和关联设备
│     ├─ 服务团队状态 +「人工」按钮：查看本轮参与并请求真人
│     └─ 新对话：新建 Conversation
└─ 设备档案
   ├─ 设备 Passport
   ├─ 已核验事实
   └─ 服务历史
```

### 客服空间

```text
客服工作台
├─ 待处理队列 / 处理概览
├─ 服务会话
│  ├─ 会话与任务列表
│  ├─ 当前客户对话
│  └─ Case 摘要、证据、AI 草稿与协作控制
├─ 服务案例
│  ├─ 案例列表 / 搜索
│  └─ Case 详情：证据 → 动作 → 审批/回执 → 核验
└─ 设备管理
   └─ Passport、事实审阅、案例历史
```

手机上的客服路径先以待处理队列列表开始；选择任务后进入同一服务工作区，通过队列/会话/服务资料切换访问上下文。消息时间线只放客户消息和已发送公开回复，AI 建议单独呈现为未发送、仅客服可见的内容；回复编辑器持续标注客户可见。服务阶段始终可见，复杂审批逐步展开；宽屏再并列显示多列信息。客服的首要操作是接手任务和发送给客户，不展示客户侧的新对话或联系人工入口。可交互评审稿见[双端手机优先原型](prototypes/mobile-first-review.html)，其中接手、消息发送等操作只演示界面反馈，不代表后端调用。

知识、策略、Guard 和经验候选管理属于主管/管理员扩展工作区，不应挤占客服接待主导航；是否为设计文档中的独立模块由权限和目标角色评审确认。

## 2. 角色任务

| 角色 | 首要任务 | 默认重要信息 | 主要操作 |
|---|---|---|---|
| 客户 | 解决当前设备/使用问题 | 当前阶段、下一步、公开对话、待确认事项 | 发送消息、上传证据、联系人工、确认结果 |
| 客服 | 接续并推动 Case | 待处理任务、最近消息、证据和事实来源、当前回复策略 | 接管、公开回复、审阅 AI 草稿、处理案例 |
| 主管/审批人 | 控制高影响动作和质量 | 待审动作、执行回执、风险与审计信息 | 批准/拒绝、复核、审核经验候选 |

## 3. 全局对象与导航规则

- **Conversation** 是客户沟通的连续入口，不承诺与 Case 一对一。
- **Service Case** 是单一问题的处理记录；能暂时没有 Device Passport。
- **Device Passport** 是长期档案；Case 来源事实先是候选，按条件核验和归档。
- 用户从服务进展进入 Case，再返回同一 Conversation；界面不能因跳转创建重复会话或案例。
- 切换客户会话时，公开草稿/内部草稿、消息缓存、事件游标按身份和会话隔离。
- 客服待处理入口是工作队列；会话列表和案例列表是可搜索、可回到来源的记录视图。

## 4. 端到端客户流程

本流程以手机上的单手使用为首要设计约束，再向平板和桌面扩展。首页突出「进入对话」，并列出历史对话与服务记录；工作区品牌栏下提供「对话 / 处理详情 / 关联设备」三个视图，新对话和人工协助作为操作按钮。

### 新问题

1. 首页只用一个主按钮「进入对话」进入服务工作区，不在首屏并列放置多个主 CTA；此入口不会自动新建 Conversation 或 Case。
2. 首页的历史对话对应 Conversation，服务记录对应 Case；两种记录分开进入，保持业务对象语义清楚。
3. 「新对话」建立新的 Conversation。聊天操作区用状态点与文字展示本轮真实参与的售后助手/专项诊断，末尾的「人工」是可点击按钮，不代表客服在线。
4. 用户描述问题后，服务端先保存消息并返回受理回执；界面显示“已收到/已保存”，不显示“诊断完成”。
5. Agent 可以追问或提供步骤；动态卡是辅助输入，普通消息仍可继续。
6. 如形成 Case，服务详情显示真实关联和当前阶段；型号未核验时明确写“型号待确认”。
7. 要求补证据时解释用途，提供上传和稍后补充两个选择。上传失败时保留原请求标识供对账。
8. 点击「人工」后在当前 Conversation 上请求人工协助。成功回执后显示已提交阶段；真实任务接管后显示客服处理中。阶段不展示推算 ETA，也不把点击动作本身当作成功回执。
9. 有售后动作时区分申请、审批、执行、Mock 回执；客户反馈结果后，后端核验再决定 Case 是否已解决。
10. 核验解决后可以提供可选评价；本次设计仅预留体验，不代表当前有 CSAT API。

### 客户端团队状态与人工入口

```text
● 售后助手 正在分析   ● 专项诊断 已参与   [○ 人工]
```

- 售后助手状态来源是当前 `agent.progress` 事件：RUNNING/LOOKUP 为本轮处理中/查资料，COMPLETED 仅代表本轮处理结束，不是 Case 已解决，FAILED 代表本次处理尝试未完成。
- 专项诊断状态来源是当前 `specialist.activity` 事件：STARTED/LOOKUP 表示诊断正在分析/查阅；RESULT_READY 表示有诊断结果；WAITING_CUSTOMER/WAITING_STAFF/FAILED 映射为相应的后续阶段。
- 仅 `PUBLIC` 事件进入客户栏；模型策略、内部活动和推测的在线状态不显示。当前后端只在 `AI_LEAD + AI_AUTO` 条件下产生这两种公开事件，并会在派发时重新校验；其他策略下活动为内部可见。
- 专项诊断没有本轮事件时不显示“已参与”。圆点是状态的辅助编码，需配合角色名称和阶段文字。
- 「人工」是按钮。真实 UI 调用现有协助请求操作；按钮点击、提交中、任务创建成功、客服接手是不同阶段。没有真实回执时不能宣称已提交/已接手。

### 已有服务继续处理

1. 客户看到按最近更新排序的历史会话和服务记录。
2. 选择一条后显示摘要、当前下一步和打开原会话的入口。
3. Case 详情和会话详情相互链接，但不重复展示一份可被误认为权威的“状态”。

## 5. 端到端客服流程

1. 工作台首先显示真实待接任务和当前活跃服务；小团队版本以处理队列为首要内容。
2. 打开任务后在同一页面查看会话历史、关联 Case 摘要、事实来源与证据，不要求客服重新收集用户已提供的信息。
3. 接管使用后端任务版本控制。若另一个客服已接管，刷新服务器状态并解释结果，不重放接管请求。
4. 选择回复方式时用中文标签展示 AI 主导/共同服务/客服主导；把“谁能对外发言”单独说明。协作模式不代表退款/换货等权限。
5. 客服以服务阶段为工作主线。会话时间线只放客户消息及已持久化的公开回复；AI 建议在独立卡片中标记“未发送 · 仅客服可见”，不伪装成已发生的消息。本阶段不提供内部记录编辑区。
6. AI 建议注明所依据的最新客户消息；新消息到达时，旧建议须失效或标为需重新核对。“放入回复框”只填充编辑器，客服检查修改后显式发送；公开发布仍由后端授权控制。
7. Case 操作独立显示审批人、动作状态和回执；UNKNOWN 提供查询原动作结果的路径，不提供重复提交按钮。
8. 结果核验由客户确认。成功核验后再显示解决态和可选评价；回访必须有同意记录。

## 6. 服务阶段词典

以下是界面表达建议，底层业务状态和任务仍由服务器记录决定。若多个 Case/任务并行，应显示具体对象，不能把 Conversation 粗暴压成单一进度值。

| 业务事实 | 客户语言 | 客服语言 |
|---|---|---|
| 新消息已受理 | 已收到你的问题 | 客户消息已保存 |
| Case `OPEN` | 已收到问题 | 待开始处理 |
| `IN_PROGRESS` | 正在处理 | 处理中 |
| `WAITING_CUSTOMER` | 等待你补充信息 | 等待客户 |
| 协助任务已创建、未接管 | 已提交人工协助 | 待接手人工任务 |
| 客服任务已接管 | 客服处理中 | 已接管 · 分配客服 |
| `WAITING_EXTERNAL` | 等待外部处理结果 | 等待外部 |
| 动作 `WAITING_APPROVAL` | 服务申请待审核 | 待审批 |
| 动作 `UNKNOWN` | 正在确认服务申请结果 | 结果待对账；查询原动作 |
| Case `RESOLVED` 且核验记录有效 | 问题已确认解决 | 已核验解决 |
| Case `CLOSED` | 服务记录已结束 | 已关闭 |
| Case 重新打开/继续处理 | 服务继续处理中 | 已重开/处理中 |

不能把 AgentRun 的 `RUNNING`、工具调用或 UI 刷新映射成“正在维修”或“已解决”。“任务已创建”也不等于“客服已接手”。

## 7. 实际 API 能力边界

真实操作以 `contracts/openapi.json` 为准；UI 文档不把 planned 提案变成可点的业务操作。

| 设计需要 | 当前 API/边界 |
|---|---|
| 登录与角色 | 本地开发 `local-auth/login`、`auth/me`、`auth/logout`；生产身份源未接 |
| 首页「进入对话」 | 仅进入 `/support` 工作区，不代表新建 Conversation 或 Service Case |
| 历史对话 | `GET /api/v1/conversations` 返回有权访问的 Conversation；消息幂等发送和 cursor 分页 |
| 新对话 | `POST /api/v1/conversations`；只有收到成功响应后才显示已创建 |
| 客户服务记录/详情 | `GET /api/v1/cases` 与 `GET /api/v1/cases/{id}`；业务服务按客户所有权过滤。设备档案用独立 Device API |
| 客服服务资料 | `GET /api/v1/conversations/{id}/case-summaries`；当前 `desk_case_summaries` 明确要求 STAFF，不能直接给客户页使用 |
| 实时协作 | authenticated SSE + 持久事件补取；按角色过滤 PUBLIC/INTERNAL；`agent.progress` / `specialist.activity` 只描述真实处理事件，不是独立的团队在线状态 API |
| 联系人工客服 | `POST /api/v1/conversations/{id}/assistance-requests`；阶段仅反映真实受理/接手状态，ETA 当前没有契约字段 |
| 协作策略 | mode transition 接收 target mode、reply policy、reason、expected version |
| UI action | 受控 action id、ui revision、expected conversation version、client action id |
| 案例/设备 | Case、Device 资源；多对多关联、事实候选/核验/撤销/归档 |
| 图片 | 上传、检查状态和授权预览；本地结构检查不是恶意扫描/视觉诊断 |
| 售后动作 | 仅开发/测试 Mock Adapter，独立审批、回执与 UNKNOWN 对账 |
| 结果核验 | 有效 Mock 成功回执 + 客户本人确认才可解决相关 Case |
| 满意度 | 尚无 API；仅作为之后的扩展设计，不显示可提交按钮 |
| 回访 | 客户同意后预约；到期只创建内部客服任务，不自动发客户消息 |

## 8. 错误与恢复体验

- `401`：提示会话需要重新登录；不丢弃尚未确认的用户草稿。
- `403/404`：明确没有权限或记录不可访问；不替换成其他客户的数据。
- `409`：说明记录已被更新，刷新对象与操作选项；不自动重放业务写入。
- `422`：在具体字段附近解释需要更正的内容。
- 网络超时/未知提交：显示“结果尚未确认”，保留原幂等 ID；先查询或用同 ID 重试。
- SSE 断开：提示实时更新暂不可用，同时继续查询持久数据；不显示为业务失败。
- 未知/过期 UI revision：让当前卡失效并刷新，提供文本备用路径。
- 加载/空/错误/无权限/停用状态都应有去向；避免“空白卡片”或只留转圈。
