# 售后通核心页面设计规格

状态：页面方案草案  
视口：手机优先定义任务顺序和触控方式，再扩展平板与桌面布局。页面具体业务状态必须由真实接口数据支撑。

本轮以[双端手机优先原型](prototypes/mobile-first-review.html)作为主评审稿。客户首页聚焦「进入对话」，并提供历史对话与服务记录入口；进入工作区后，品牌栏下使用「对话 / 处理详情 / 关联设备」三个视图导航。新对话是工作区操作；对话区以服务团队状态和唯一的「人工」按钮呈现协作与人工入口。原型不调用 API，也不代表这些交互已接入生产前端。

## 1. 客户服务首页

### 页面任务

让客户一眼找到对话入口。历史服务与设备是进入服务工作区后的次级任务。

### 层级

1. 顶部只保留紧凑品牌、账户入口；窄屏不出现桌面式文字导航。
2. 一句清楚的欢迎/说明和一个突出按钮「进入对话」是首屏主视觉；不并列设置多个大 CTA。
3. 入口按钮打开服务工作区。工作区再提供「新对话」以及真实 Conversation/Case 的访问入口。
4. 设备档案是次级浏览内容，不与对话入口争夺首屏注意力。

手机首屏优先呈现品牌、简短说明和唯一主操作：

```text
+----------------------------+
| 品牌                  账户 |
+----------------------------+
| 售后服务，从对话开始。     |
| 一句话说明                 |
|                            |
| [       进入对话      ]   |
+----------------------------+
```

进入工作区后，所有设备尺寸使用同一组清晰入口；宽屏可将内容并列呈现：

```text
+----------------------------------------------------------------+
| 品牌       对话      服务记录      关联设备             账户    |
+----------------------------------------------------------------+
| 当前服务                         [新对话]                     |
| ● 售后助手 正在分析 · ● 专项诊断 已参与 · [○ 人工]          |
| 对话      处理详情      关联设备                            |
| 历史 Conversation / 服务 Case / 当前消息与资料                 |
+----------------------------------------------------------------+
```

### 空态和异常

- 无历史：让客户从「进入对话」入口开始；不展示虚构案例卡片。
- 无设备：允许继续开始服务；告知设备信息可以稍后补充。
- 列表读取失败：保留页面标题和重试动作，区分服务不可用与无记录。

### 入口到服务的状态转换

- 首页「进入对话」是入口，不表示已创建 Conversation 或 Case。真实实现可根据用户身份进入最近服务，也可继续让用户选择历史；选择行为应明确。
- 工作区将历史对话（Conversation）与服务记录（Service Case）分开呈现；点选历史服务后打开原 Conversation 和真实关联资料，不创建重复对象。
- 工作区的「新对话」创建新的 Conversation；只有真实 API 成功后，才能展示新的会话已建立。
- 工作区提供返回首页路径。返回不丢输入草稿或当前选择；真实实现须由前端路由/状态恢复保证，当前静态原型只演示页面状态切换。
- 对话操作区显示服务团队参与状态：「售后助手」和「专项诊断」仅按真实且对客户可见的活动事件显示；「人工」是可点击按钮，不是在线状态灯。请求成功后只显示后端确认的服务阶段，不显示预计等待时间。
- 对话与阶段均使用客户可理解语言；不显示内部备注、Agent 原始推理或 `AI_LEAD` 等内部枚举。
- 当前无满意度 API，未核验解决前后都不出现可提交的评分控件；未来仅在真实解决回执后定义可选评价。

### 手机布局要求

- 先完成单列首页和唯一对话入口，再用桌面宽度增加并列信息；不把桌面三列缩小塞进手机。
- 进入服务后默认打开对话。品牌栏下用「对话 / 处理详情 / 关联设备」三个短视图入口；历史对话与服务记录从首页进入，「新对话」作为工作区操作；服务团队参与栏末尾的「人工」是唯一人工协助入口。
- 当前对话占据可用高度；消息列表在中间滚动，输入区固定在工作面板底部，并适配系统安全区和软键盘。输入、发送、附件、人工入口等主要触控目标不小于 44 CSS px。
- 服务详情在自己的面板中阅读，信息较长时可滚动；用户仍能通过固定切换控件回到对话。
- 首页「进入对话」和工作区按钮应有清楚焦点态、读屏名称与可见按下反馈。历史对话和服务记录有清楚不同的副标题/摘要，避免用户误以为它们是一份列表。
- 目标验收视口包括 360×800、375×812、390×844 手机，768×1024 平板以及 1280×800 桌面。最新重定位版已在约 1260×708 浏览器窗口检查首页与视图切换；目标手机尺寸、窄屏导航和软键盘弹出状态仍待复核。

## 2. 客户服务会话

### 页面任务

在一处完成持续沟通，查看本次服务上下文，并知道当前唯一优先的下一步。

### 手机优先布局

```text
+--------------------------------+
|  服务记录  当前对话  服务详情  |
+--------------------------------+
| 当前问题 / 当前阶段            |
|                                |
| 消息记录（独立滚动）           |
|                                |
| 补充信息 / 安全提示             |
+--------------------------------+
| ● 售后助手 正在分析 ● 专项诊断 已参与 [○ 人工]|
| [附件] 输入消息        [发送]   |
+--------------------------------+
```

团队参与栏按一行优先排布；窄屏允许自然换行，不能出现横向滚动或缩小触控区。状态点旁必须同时有文字，不能仅靠颜色传递状态。当前静态示例显示「售后助手 正在分析」「专项诊断 已参与」；真实产品必须由当前轮次的持久事件和 PUBLIC 可见性驱动，不能把固定示意状态当成已实现实时状态。

- `agent.progress` 的 RUNNING/LOOKUP 仅表明当前请求正在处理或查阅资料；可映射为客户能理解的「正在分析 / 正在查阅资料」，不得映射为设备维修或问题已解决。只有事件 PUBLIC 且仍符合当前协作/回复策略时客户可见。
- `specialist.activity` 的 STARTED/LOOKUP 表示专项诊断正在分析/查阅；RESULT_READY 表示有诊断结果；WAITING_CUSTOMER/WAITING_STAFF/FAILED 应转为对应下一步语义。只有 PUBLIC 的活动可进入客户团队栏，内部活动不得泄露。
- 专家不存在本轮活动时，不显示「已参与」灯号；失败或结束也不永久保留为活跃灯。静态原型所示内容为视觉示例。
- 「人工」按钮点按后，真实实现调用现有协助请求操作。提交中使用按钮禁用/忙碌反馈；成功后按 TaskRead/真实事件展示“已提交人工协助”或“客服已接手”等阶段；失败保留可重试路径。不能因点击本身宣称任务已创建，也不另造排队 ETA。

手机进入工作区后默认选择“对话”；切换对话、处理详情和关联设备时保持当前 Conversation、草稿与各面板阅读位置。消息区单独滚动，输入区固定在工作区底部并考虑系统键盘和安全区。

### 宽桌面草图

```text
+--------------------------------------------------------------------------------+
| 品牌        对话       服务记录       关联设备                         账户    |
+--------------------------------------------------------------------------------+
| 会话历史                 当前问题 / 服务阶段                    本次服务资料    |
| [搜索]                   问题标题  当前业务状态                  当前阶段       |
| [会话行]                 --------------------------------       下一步         |
| [会话行]                 客户与已发送公开回复                      关联 Case     |
| [会话行]                 当前阶段/必要风险提示                     关联设备      |
| [会话行]                 AI 建议 · 未发送 · 仅客服可见               任务/回执     |
|                          [回复客户 · 客户可见]                      |
|                          [附件] 输入消息...                 [发送给客户]   |
+--------------------------------------------------------------------------------+
```

手机优先使用单面板工作区并默认打开对话，品牌栏下使用「对话 / 处理详情 / 关联设备」三个视图入口；历史对话和服务记录从首页打开。「新对话」是操作按钮；对话区团队参与状态旁的「人工」按钮请求人工协助。平板延续同一切换模式。宽桌面才展开消息主区和服务资料。消息区永远是主区；上下文资料避免重复长篇复述。切换面板须保留草稿和当前选中会话。

### 消息与内容优先级

1. 已持久化的客户与客服公开消息。
2. 安全提醒、客户当前待办、证据上传卡。
3. 由真实 Case/任务/核验投影生成的服务阶段。
4. AI 专家/工具生命周期默认不进入客户消息流；任何运行状态都不能替代服务结果。
5. 页面右栏放 Case/设备摘要和唯一的人工协助入口。点按后显示提交状态；只在后端确认任务创建后显示已提交。

### 发送状态

`本地待发送 → 服务端已保存 → 处理中/等待/客服处理（由事实决定） → 公开回复/客户下一步`。超时显示结果待确认并保留同一 `client_message_id`；不得无幂等键新建第二条消息。

## 3. 客户服务记录列表与详情

### 列表任务

扫描所有 Case，按更新时间/状态筛选，打开想继续处理的问题。

```text
+--------------------------------------------------------------+
| 服务记录                                  [开始新服务]      |
| [全部] [处理中] [等待我] [已解决]    [搜索问题]              |
| 问题标题             关联设备       当前阶段       最近更新  |
| ...                                                          |
+--------------------------------------------------------------+
```

筛选项只根据 API 当前返回的 Case 状态定义，不在前端把会话归档状态当作 Case 完成状态。

### 详情任务

- 顶部：Case 问题、状态、创建时间和回到来源会话入口。
- 主区：由业务记录构建的阶段时间线，区分已发生、当前等待、未来可能步骤。
- 侧区：关联设备和已核验事实；空设备身份明确标记待确认。
- 动作详情：客户可读的 Mock 明确说明；审批、回执和结果核验不合并为一个完成勾选。
- 核验：展示客户提交的 WORKING / NOT_WORKING / UNCERTAIN 和服务端 decision。
- 评价：只在核验解决后作为可选设计位；未有评价 API 前不显示提交控件。

## 4. 客服工作台

### 页面任务

找到下一件应处理的工作，并用最短路径进入同一会话和 Case。

### 首屏优先级

1. 待接人工任务和已分配但未处理项。
2. 等待客户/外部、待审批、UNKNOWN 对账等需要动作的项目。
3. 活跃服务概览和搜索/过滤。
4. 辅助指标在次级层，只有存在真实统计接口和定义后展示。

```text
+--------------------------------------------------------------------------------+
| 客服导航 | 工作台                                                   账户       |
|          | [待接 4] [处理中 8] [待审批 2] [未知结果 1]                       |
|          | 处理队列                                                   [搜索]   |
|          | 优先级/等待状态   问题/客户   最近消息   更新   [打开会话]            |
|          | -------------------------------------------------------------------  |
|          | ...                                                                 |
+--------------------------------------------------------------------------------+
```

队列优先级需要后续按业务规则定义；初版不显示没有后端字段支持的 SLA/剩余时间。

### 手机优先布局

- 默认进入待处理队列；每个任务用摘要行呈现客户、问题、当前业务阶段和最近消息，不以横向滚动表格呈现。
- 打开一项任务后进入单列会话工作区，以“队列 / 会话 / 服务”切换列表、公开沟通和上下文资料；当前客户和当前服务持续可见。
- 消息时间线仅展示客户消息和已持久化的公开回复。AI 建议位于独立的「未发送 · 仅客服可见」卡片中，不能渲染为消息气泡或伪装成已发生的会话事件。
- 回复编辑器固定标识回复对象和受众「回复客户 · 客户可见」。AI 建议的「放入回复框」只填充编辑器，不发送；客服可检查、修改后再点击「发送给客户」。本阶段不设置内部记录编辑区。
- AI 建议应关联其生成时依据的最新客户消息；若出现更新的客户消息，旧建议标记为过期/需重新核对，不再作为可直接采纳的最新建议。
- AI 草稿及审批详情在当前会话内分段展开或使用可返回的详情面板，不要求手机端同时展示多列。
- 接管、发送、审批等操作至少 44 CSS px，错误/冲突说明紧邻所影响的操作；不使用 hover 才可发现的操作。
- 宽屏客服继续使用队列、会话、服务上下文分栏；手机的单列与切换模式才是首要验收路径。
- 双端手机优先评审稿：[mobile-first-review.html](prototypes/mobile-first-review.html)。在评审稿中，客服可从队列打开示例任务，切换会话与服务资料；客户消息和 AI 草稿分别位于公开消息时间线与客服专属建议区，所有提交操作均为静态示意。
- 客服当前阶段只显示业务阶段，不估算排队时间；AI 草稿必须经过客服审阅后才能由有权限的服务端公开；本阶段不设置内部记录编辑区。界面标签是角色可读文案，`AI_LEAD` / `CO_SERVICE` / `HUMAN_LEAD` 等枚举不直接展示。

## 5. 客服服务会话

### 桌面草图

```text
+--------------------------------------------------------------------------------+
| 客服导航 | 会话列表              当前 Conversation                 服务上下文   |
|          | 搜索/过滤              客户 + 当前 Case                  Case 摘要     |
|          | 待接/处理中            公开消息与必要安全提示             证据/事实     |
|          | 每行最近消息           已发生的公开消息                        协作策略     |
|          |                        AI 建议 · 未发送 · 仅客服可见             任务/动作     |
|          |                        回复客户 · 客户可见 + 发送按钮       时间线       |
+--------------------------------------------------------------------------------+
```

### 关键行为

- 接管时明确显示“接管/已接管”；409 后刷新任务并隐藏过期操作。
- 时间线仅包含已保存的客户消息和 PUBLIC 回复；AI 草稿独立显示“未发送 · 仅客服可见”，绝不作为一条已发送消息混入时间顺序。
- 编辑器持续显示“回复客户 · 客户可见”。采纳建议只填充编辑器，发送仍由客服显式触发并经后端授权。
- 客户新消息到达后，关联旧消息的建议须标记过期或要求重新核对；发送失败/未确认时沿用真实消息回执语义，不在时间线伪造成功消息。
- 当前不展示内部记录编辑器；客服专属 INTERNAL 活动可在授权服务资料/诊断区域查看，不进入客户可见消息流。
- 策略用“AI 主导 / 共同服务 / 客服主导”显示，旁边解释“AI 是否能直接回复”。审批能力另按角色与动作单独呈现。
- 切换策略造成旧卡失效时说明状态已更新，并刷新卡片，不保留看似可用的陈旧按钮。
- 专家分析显示结论假设、证据来源和置信说明；原始模型推理不可显示。

## 6. 客服 Case 详情

- **问题与来源**：客户原始描述、渠道和关联会话。
- **事实与证据**：已核验、候选、未知、撤销状态分组；每项显示来源。
- **工作流程**：真实任务、动作、审批和回执按事件顺序投影。
- **可执行操作**：只显示当前角色、记录状态和版本允许的操作；高影响动作展示后果与审批要求。
- **结果核验**：客服可读记录、不可代客户提交确认；失败/不确定时提供继续服务路径。
- **设备归档**：Case 来源事实仅在核验与 Case 条件满足后提供归档操作。

## 7. 页面状态验收矩阵

| 页面/组件 | 必须覆盖状态 |
|---|---|
| 首页与列表 | 首次加载、空态、加载失败、部分数据、筛选无结果、重试 |
| 消息发送 | 草稿、发送中、服务器已保存、未知结果、4xx 拒绝、离线恢复 |
| 人工协助 | 可请求、提交中、已创建任务、重复请求重放、无权限/会话冲突 |
| 证据 | 选择文件、上传中、检查中、可预览、拒绝、未知上传、不可用 |
| Case 动作 | 待审批、拒绝、执行中、UNKNOWN 对账、Mock 成功/失败 |
| 结果核验 | 待客户、工作/未工作/不确定、解决、继续处理 |
| 客服并发 | 任务已被接管、版本冲突、策略被他人更新、旧卡失效 |
| UI 文档 | 尚无文档、加载、支持渲染、未知组件 fallback、过期 revision |
