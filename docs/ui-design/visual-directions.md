# 客户服务页面 · 视觉方向探索

状态：组合流程方案待评审；A/B 视觉方向和新的双端手机稿均为设计提案，尚非最终品牌规范  
日期：2026-10-17  
主评审原型：[双端手机优先稿](prototypes/mobile-first-review.html)；视觉历史参考：[客户服务连续体验](prototypes/customer-service-flow.html)、[A/B 视觉对比稿](prototypes/visual-exploration.html)

## 目标

把客户手机体验收敛为单一对话入口和服务内操作：首屏以「进入对话」作为唯一突出 CTA，进入工作区后以按钮访问对话、历史 Conversation、服务 Case 和当前详情；「新对话」与「联系人工客服」留在独立操作区。客服侧则由工作队列进入任务，以服务阶段为主线。

本轮没有修改 React/CSS 页面或后端规则。示例场景为虚构的蓝牙音箱配对问题，与参考图片中的设备和案例不同。

## 参考图中抽取的设计线索

- 白色/浅色内容表面，背景保持轻柔的中性色。
- 深蓝标题与明亮品牌蓝操作形成清晰层级。
- 宽桌面上让服务记录、当前对话、阶段与设备资料形成可预测的区域；手机不沿用缩小版三栏。
- 当前阶段和客户下一步有明确视觉权重，交互卡片围绕真实待办展开。
- 手机先呈现当前任务；进入服务后以明确面板切换访问服务记录、对话和详情，保留当前服务上下文。

截图只提供视觉与布局参考，不复制其中的人名、问题标题、时间、设备图片、消息内容或进度承诺；插图为本原型内的原创矢量表达。

## 方向 A · 品牌欢迎式

**版式：** 顶部品牌导航；宽幅欢迎区以明确主标题、新服务入口和原创设备矢量插图建立识别；下方并列服务历史与当前对话；当前需要客户完成的一步以单独的暖色提示条收束。

**视觉取舍：** 留白和柔和蓝色层次更明显；欢迎区域建立情绪与品牌感；客户重新进入服务时先感知“这里可以继续帮我处理”。页面纵向内容更多，当前服务工作区开始位置较低。

## 方向 B · 精密服务工作区

**版式：** 页面标题和“开始新服务”并置；主要工作区将服务列表、对话、当前阶段与关联设备并列呈现；下一步置于侧栏顶部，人工入口靠近上下文信息。

**视觉取舍：** 更快进入正在处理的问题；阶段、证据和设备信息靠近对话，便于随时核对；信息密度比 A 高，品牌叙事和装饰空间较少。

## 两个方向共用的体验规则

- 服务阶段只用来表达当前真实阶段，不显示未经支持的等待时长。
- 用户陈述与已核验设备事实分开展示；用户提供的信息不会自动升级为已核验事实。
- “联系人工客服”保持为一个明确入口，提交后继续在当前会话服务。
- 附件、发送和人工入口在原型中不触发真实操作。
- 客户页面不呈现客服内部记录和 Agent 原始推理；客服视图突出服务阶段；AI 草稿只供客服审阅。当前小团队阶段不设置内部记录编辑区。
- 客服手机工作区从处理队列开始；打开任务后在处理队列、客户会话、服务资料之间单面板切换。公开消息只进入对话时间线；AI 建议在单独的未发送卡片里审阅，并插入客户可见的回复编辑器；客服以服务阶段推进处理，不设置内部记录编辑区。
- 当前双端手机评审稿见[mobile-first-review.html](prototypes/mobile-first-review.html)。客服示例展示阶段、设备待核验信息和协作策略文案，不展示等待时长；所有人物、状态和消息均为虚构内容。

## 手机优先客户主流程

```text
首页：简短说明 + [进入对话]
  ↓
工作区导航：对话 / 处理详情 / 关联设备；首页提供历史对话与服务记录入口
  ├─ [新对话] → 创建新的 Conversation（真实接口确认后显示成功）
  └─ [联系人工客服] → 当前 Conversation 的人工协助请求
```

首页不重复展示完整聊天区或最近记录列表，首屏只有一个主要选择。进入服务后，导航入口按内容分类；操作按钮在另一组显示。历史对话对应 Conversation，服务记录对应 Case。宽桌面可以展开上下文，手机优先保证对话和阶段可读。客户看到真实阶段，不展示等待 ETA。新服务示例不暗示 Case、设备档案或后台任务已创建；只有真实接口确认后，产品实现才可显示已创建。

主评审稿中「进入对话」「新对话」「联系人工客服」只演示界面流程，不调用后端。人物、服务案例、日期、阶段和设备示例均为虚构。当前没有评价接口，因此流程不加入满意度提交控件；后续真实核验解决并具备评价契约后，再设计完成回执。

## 评审与收敛

建议先走通组合原型，再回看 A/B 对比稿判断欢迎区与工作区的比例。评审通过后：

1. 先确认手机的组合流程、入口命名、工作区层级、单手触达和键盘状态，再确认宽屏扩展。
2. 将确认结果回填到 `visual-system.md` 和 `page-specs.md`，形成可实施的视觉与页面规格。
3. 再按实际 React/API 边界拆解真实前端改造；逐项以真实回执驱动成功状态。

原型实现静态交互；页面截图不代表 API、服务任务或设备信息已经存在。
