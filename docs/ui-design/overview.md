# 售后通前端设计总纲

状态：设计基线草案，供产品与设计评审  
日期：2026-10-17  
范围：客户与客服 Web 体验、信息架构、视觉系统、关键状态与渐进实现路线。

当前阶段产物：[独立静态 UI 评审原型](prototypes/README.md)，包含客户/客服交互结构、客户 A/B 视觉探索、客户连续体验，以及新的[双端手机优先评审稿](prototypes/mobile-first-review.html)。评审稿可切换客户和客服角色，浏览客服的队列、会话和服务资料；原型用于评审流程、视觉和信息层级，不连接真实服务或提交业务操作。评审结论应先回填本设计基线，再进入应用实现。

## 1. 设计目标

打造可信、精致、具有品牌辨识度的售后服务界面。客户能持续完成一个真实服务任务；客服能接续上下文并处理工作；两种角色看到的服务事实保持一致，信息密度和解释方式按角色调整。

本设计从产品目标、领域规则、真实 OpenAPI 与用户提供的界面图出发。参考图只用于提取视觉和布局线索，不将截图中的设备、身份、时间、诊断、状态或承诺作为业务事实。现有前端代码不是视觉方向或布局来源。

## 2. 产品体验承诺

1. 一个连续服务入口承接对话；一个 Conversation 可关联零到多个 Service Case，Case 可关联零到多个设备。
2. 服务进度仅表达真实业务记录：用户待办、客服任务、Case 状态、动作回执和核验结果。
3. 用户陈述、候选事实、已核验事实、模型假设、Mock 回执使用不同标签与说明。
4. 客户只能看到 PUBLIC 内容；客服在授权后查看 INTERNAL 内容。AI 是否可以对外发布由后端当前授权策略决定。
5. 没有设备身份也可以开始报障。客户提供的设备资料不会自动升级为可信 Device Passport 事实。
6. 交互卡片是业务事实的受控投影，不是数据源；卡片不可用时，文本和固定交互仍能继续服务。

## 3. 设计方向

### 推荐方向：明亮、精密、温暖的专业服务

- 使用高明度中性画布和白色内容表面，以品牌蓝承载主要操作与选中状态。
- 用墨蓝文字、克制的边界、精细间距和清楚的排版建立质感；减少无意义的大面积渐变、重阴影和重复卡片。
- 客户侧降低信息密度，突出当前问题、服务阶段和下一步。
- 客服侧提高扫描效率，突出队列、会话、案例事实与可执行操作。
- 状态颜色用于语义，不作为装饰；颜色外必须有文字、图标或形状提示。
- 圆角和阴影按层级使用：页面区块优先靠留白、分隔和版式建立关系；浮层/菜单才使用明显投影。

这是依据参考图所提出的推荐方向，不是对图片的像素复刻。参考图中三栏对话、详情时间线、关联设备和蓝色主操作作为方向输入；样例内容仅作构图素材。

### 客户入口与服务内操作

客户首页以一个「进入对话」主按钮为首要入口，同时像参考图一样在下方提供可点开的「历史对话」和「服务记录」行。进入服务工作区后，品牌栏下的轻量导航只放三个当前视图：「对话」「处理详情」「关联设备」；「新对话」和团队状态栏末尾唯一的「人工」按钮是上下文操作，不塞进导航。历史对话读取 Conversation，服务记录读取 Service Case；两者有关联，但不是同一份列表。

客服不复用客户的服务导航：默认进入处理队列，打开任务后再切换「处理队列 / 客户会话 / 服务资料」。客户端强调容易继续服务；客服端强调谁需要处理、当前阶段和下一项可执行动作。

## 4. 用户与客服的体验地图

### 客户

```text
首页：「进入对话」主按钮 +「历史对话」「服务记录」入口
        ↓
服务工作区导航：对话 / 处理详情 / 关联设备
        ├─ 对话 ──→ 查看真实服务参与者；补充文字或照片；点「人工」请求真人
        ├─ 新对话 ──→ 新 Conversation
        └─ 服务核验 ──→ 未解决继续处理 / 已解决后可评价（待接口）
```

### 客服

```text
处理队列
   ↓
接管待处理任务 ──→ 阅读同一会话与授权摘要
   ↓
选择回复责任与 AI 协作方式
   ├─ 公开回复
   ├─ AI 草稿（客服审阅后决定是否公开）
   └─ Case 操作：申请 → 审批 → 执行 → 回执
                                  ↓
                            客户核验 → 结束/继续处理
```

客服模式的产品化标签：`AI_LEAD` =「AI 主导」，`CO_SERVICE` =「共同服务」，`HUMAN_LEAD` =「客服主导」。这些是客服工作策略，不是 Case 状态，也不赋予外部动作权限。

## 5. 视觉参考的使用

用户提供的五张参考图及来源记录：[2026-10-17 客户服务界面参考图](../design-references/2026-10-17-customer/README.md)。主要抽取：

- 顶部清晰的身份和一级导航；
- 对话与服务详情之间的可预测切换；
- 桌面端历史列表、消息和服务资料的分区布局；
- 当前阶段和客户下一步有较高视觉权重；
- 轻表面、蓝色主要动作、状态标签以及明显的文字层级。

本轮调研补充了成熟产品与平台规范：Intercom 支持直接进入对话，同时保留访问其他空间的入口；其 Messenger 也能配置新对话和历史消息入口。Apple 将 tab bar 定义为一级内容导航，并建议用工具栏承载当前页面操作、标签保持简短并避免过多入口。因此本方案让品牌栏下的三个视图采用轻量文字导航与选中下划线；历史/服务记录留在首页列表，新对话和「人工」作为独立操作。Apple 对按钮 hit region 的一般建议为 44×44 pt；Web 无障碍最低标准 WCAG 2.2 AA 是 24×24 CSS px（有例外），本项目将 44 CSS px 作为常用手机操作的设计目标。[Intercom Messenger](https://www.intercom.com/help/en/articles/6612589-set-up-and-customize-the-messenger) · [Apple Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars/) · [Apple Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons/) · [WCAG 2.2 Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)。

### 服务团队指示与客服草稿呈现

本轮参考成熟客服产品的两个稳定模式：Intercom 把 Copilot 作为客服工作区的助手，建议由客服审阅/编辑后发送；Zendesk 明确区分公开回复和未发送草稿，并在 AI 转人工后切换对外回复责任。Intercom 也通过正在处理会话的同事头像帮助客服避免重复作业。我们借鉴“真实参与者可辨”和“草稿不等于消息”，不照搬产品结构：[Intercom Inbox AI](https://www.intercom.com/help/en/articles/6955446-ai-features-available-in-the-inbox) · [Intercom Inbox](https://www.intercom.com/help/en/articles/6258745-the-inbox-explained) · [Zendesk composer](https://support.zendesk.com/hc/en-us/articles/4408831849882-Composing-messages-in-the-Zendesk-Agent-Workspace) · [Zendesk handoff](https://support.zendesk.com/hc/en-us/articles/4408824482586-Managing-conversation-handoff-and-handback)。

- 客户端采用「● 售后助手 正在分析　● 专项诊断 已参与　[○ 人工]」的信息结构。助手和专项诊断状态只从当前轮次真实、PUBLIC 事件映射；无事件时不显示“已参与”。「人工」本身是可点击按钮，不表示真人在线；请求成功/客服接手仅按后端回执更新阶段，不提供 ETA。
- 后端已有 `agent.progress` 与 `specialist.activity` allowlist 持久事件，不是在线 presence API；当前只有 `AI_LEAD + AI_AUTO` 可对客户公开，且 Outbox 派发时会再次校验。客服主导/共同服务等内部活动不能推导成公开灯号。
- 客服消息时间线只放已保存的客户消息和公开回复；AI 建议移出时间线，单独标记“未发送 · 仅客服可见”，注明依据的客户消息。把建议放入回复框只填文本，不发送；客服检查、修改并点发送后，收到真实保存回执才成为对话消息。
- 如果更新的客户消息晚于草稿依据消息，草稿过期或提示重新核对。客服端编辑器始终说明“回复客户 · 客户可见”，避免误将 AI 草稿、公开回复切换操作混为一类。

设计系统 Skill 的检索建议了高对比的专业蓝、清晰焦点态、减少装饰、手机响应视口和可访问触控目标。我们沿用用户参考图的品牌蓝与明亮表面，不照搬通用配色模板；具体 token 仍以[视觉系统](visual-system.md)为本项目提案。

布局按手机优先设计：小屏首页采用单列，一个「进入对话」主按钮下方列出历史对话与服务记录入口；服务工作区默认显示对话，并通过品牌栏下的「对话 / 处理详情 / 关联设备」切换视图。宽桌面再展开会话与服务资料并列布局。

## 6. 设计决策记录

| 决策 | 当前建议 | 依据/状态 |
|---|---|---|
| 首要产品体验 | 连续服务工作区；新问题和历史服务都可进入 | V1 用户旅程、参考图 |
| 客户端壳层 | 对话、服务记录、设备；账户操作独立 | 待产品评审的 IA 建议 |
| 客户手机首屏 | 单一「进入对话」按钮；进入后再显示导航和服务操作 | Intercom 直接进入对话模式、用户上传参考图；原型方案，待评审 |
| 对话与服务记录 | 历史对话对应 Conversation；服务记录对应 Service Case | 产品领域模型；不能合并成一份语义含混的历史列表 |
| 服务内操作 | 「新对话」与团队参与状态末尾的「人工」是明确按钮，不混入内容标签栏 | Intercom 空间与 CTA 配置；Apple 导航/操作区分 |
| 客户对话布局 | 首页主按钮与历史记录入口；工作区以对话、处理详情、关联设备切换；参与状态与人工按钮同栏呈现 | 参考图首页/聊天/详情的页面层级；静态原型已调整，手机视口待验收 |
| 客服工作台布局 | 手机先展示处理队列；选中任务后在队列、会话、服务资料间切换；宽桌面并列 | 适合当前小团队的设计建议；后续按真实任务/API校准 |
| 状态表达 | 用户看阶段和下一步，客服看任务与可审计细节 | V1 真实进度规则 |
| 满意度 | Case 核验解决后展示可选评价；不代替核验 | 当前无评价 API，设计预留，未实现 |
| ETA | 阶段状态即可；不展示无接口支持的等待时长 | 现有契约没有 ETA |
| 客户主流程布局 | 手机首屏聚焦「进入对话」；工作区分开展示历史 Conversation 与服务 Case；对话操作区显示真实团队参与状态并保留唯一人工按钮 | [双端手机优先原型](prototypes/mobile-first-review.html)；组合方案待评审 |
| 客服消息展示 | 时间线仅呈现已发生的公开消息；AI 建议在独立未发送卡片审阅并插入固定的客户可见编辑器 | [客服会话页规格](page-specs.md)、[双端手机优先原型](prototypes/mobile-first-review.html)；静态交互稿 |
| 风格探索记录 | A「品牌欢迎式」和 B「精密服务工作区」保留为构成组合方案的两种视觉取舍 | [视觉方向说明](visual-directions.md)与对比原型 |

## 7. 不在本轮设计范围

- 不修改前端 React/CSS，不改变后端 API、Schema 或业务规则。
- 不将 Mock Adapter 说成真实 Anker 售后系统。
- 不设计以截图演示数据为内容的生产页面。
- 不把未经确认的生产认证、客服排班/ETA、CSAT、远程设备诊断设计成已有能力。
- 不建设通用 CRM、通用 Agent 页面生成器或与服务任务无关的动效系统。
