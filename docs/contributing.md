# 协作开发指南

本指南说明当前仓库如何拆分和集成工作。产品规则以[产品定义](product-definition.md)、[系统架构](architecture.md)、[领域与接口契约](domain-and-contracts.md)、[开发实施计划](development-plan.md)四份 V1 文档为准；完成状态结合计划勾选和阶段验收记录判断。开始任务时先查实际代码及[现有项目合并说明](baseline-integration.md)，将设计目标与现有能力分开记录。

## 当前工作面

| 工作面 | 活动入口 | 变更时共同核对 |
|---|---|---|
| 业务数据与迁移 | `backend/serviceos_api/persistence/`、`backend/migrations/` | Case、Conversation、Device 的独立性、租户约束、版本与升级路径 |
| 应用服务与权限 | `backend/serviceos_api/application/` | 资源授权、业务状态、幂等及公开消息发布边界 |
| HTTP 契约 | `backend/serviceos_api/api/`、`backend/serviceos_api/application/contracts.py` | 路由与 Schema 真实存在，错误语义与 OpenAPI 一致 |
| Agent 与异步执行 | `backend/serviceos_api/agents/`、`backend/serviceos_api/worker/` | Worker 租约、Checkpoint、应用服务写入和恢复时的副作用 |
| Web | `frontend/src/` | 当前 API 类型、用户/客服可见性、失败与重试状态 |

这是现有文件位置，不表示每个领域已经有独立模块。当前 `api/business.py` 与 `application/services.py` 包含多个业务对象；拆分时保持原有服务校验和路由契约，避免产生第二套规则。已归档原型不参与活动实现。

按模块上手见[前端开发指南](../frontend/README.md)和[后端与 Worker 开发指南](../backend/README.md)。五张设计图的视觉转译见[界面设计指南](ui-design-guidelines.md)，图片中的示意操作仍需依赖真实业务 API。

## 契约先行：同一场景，双方独立推进

V1 的统一接口目标放在[完整 OpenAPI 提案](../contracts/proposed/v1/openapi.yaml)，其来源和未实现范围见[提案说明](../contracts/proposed/v1/README.md)。一个跨前后端的功能切片开始编码前，由前端、业务后端及需要时的 Agent/Worker 负责人共同核对这份提案，并填写[功能契约模板](templates/feature-contract.md)，存入该功能的 `specs/<功能名>/contracts/`，补充用户场景、权限和验收决策。集成负责人确认以下内容已经明确，才把该切片标为“契约已确认”：

- 用户从哪个入口完成什么事，以及 `/support`、`/desk` 各自应看到的真实结果；Case、Device、Conversation、Task 的归属关系。
- 每个拟新增或变更的 HTTP 操作：请求和响应示例、字段含义、必填与限制、成功状态码；列表的分页和排序规则。
- 身份、租户和资源权限，PUBLIC/INTERNAL 可见性；认证失败、无权限、校验失败、版本冲突、重复请求及不可用时的错误语义。
- 写入操作的幂等键、资源版本与并发规则；异步任务的受理回执、持久事件、SSE 补取与恢复方式；需要刷新哪些读模型或 UI revision。
- 前端加载、空态、提交中、成功、拒绝、重试、断线和旧版本状态；后端成功、拒绝、并发和恢复测试；最终由谁按浏览器路径验收。

**拟定契约**是双方开工的共同设计，可先于代码存在，但不证明路由可用。提案中 `x-serviceos-status: planned` 的操作尚不能调用；`contracts/openapi.json` 是从当前真实 FastAPI 路由导出的**已实现契约**，`frontend/src/api/schema.d.ts` 只从它生成。不得把拟定接口加入活动 OpenAPI、注册返回假成功的路由，或把未接通的前端操作显示成已完成。

契约确认后可以并行：前端完成页面结构、展示组件和各状态，后端完成应用服务、权限、路由、Schema、迁移及测试，Agent/Worker 在已约定的命令和事件边界内开发。前端尚无真实接口时，可实现不提交业务结果的界面和状态结构；实际提交、成功提示与生成 Client 接入须等真实路由落地。联调时由后端导出 OpenAPI，前端生成类型，再共同验证同一场景。契约字段或语义发生变化，先更新功能契约并通知依赖方，由集成负责人协调版本与合并顺序；不能让两边各自猜测。

## 拆分任务与并行工作

1. 每项工作写明所处阶段、验收场景、拟改文件、依赖及一个集成负责人。共享 Schema、迁移、路由和事件先按上节确认契约；不共享这些边界的界面、业务和文档工作可以直接并行。
2. 跨 Case、Conversation、Device 的写操作由应用服务维护不变量；Agent 工具只调用类型化服务命令。用户可见消息和公开事件由 Conversation Service 检查当前协作策略与可见性。接口审阅同时核对成功、拒绝、重复请求与过期版本路径。
3. API 变更按“共同确认拟定契约 → 分头实现 → 后端完成路由、Pydantic Schema、应用服务与测试 → 导出 `contracts/openapi.json` → 前端运行 `generate:api` 并接入真实请求 → 联调验收”的顺序推进。目标接口仅写在 V1 设计表中时，还须把该切片的操作契约细化并确认；不添加假成功端点。
4. 迁移、权限策略、状态机和公开事件格式属于共享边界。并行分支变更同一边界时，由集成负责人先合并并验证契约，再让依赖方更新到新版本；冲突按 V1 业务规则和实际测试解决，不按文件时间先后覆盖。

### 三人交接约定

| 责任人 | 主要工作 | 交给下一人的可检查结果 |
|---|---|---|
| 业务后端与契约 | 应用服务、权限、迁移、HTTP 路由、Pydantic Schema | 成功/拒绝/幂等/过期版本测试和已导出的 OpenAPI |
| Agent 与 Worker | 受控工具、任务、重试、Checkpoint、AgentRun | 调用应用服务的类型化命令及失败/恢复测试；不直接写业务状态 |
| Web 前端 | 客户/客服页面、事件呈现、生成 Client、响应式状态 | 基于当前 OpenAPI 的类型检查、构建及真实数据交互验收 |

一项跨模块需求先由业务后端与使用方共同确认拟定契约，再各自实现。业务后端实现并导出已实现契约后，前端负责人更新生成类型并接入请求；Agent 负责人按类型化命令接入服务。集成负责人最后验证客户/客服隔离、拒绝路径、断线和重试。工作区代码和 Spec Kit 任务可以领先于阶段勾选；只有验收证据充分时才更新完成状态。

## 变更集成

- 一个变更集说明目标、涉及的业务边界、实际改动文件、验证命令及结果、未实现项。修改设计时同步标注计划状态；只有满足阶段验收且有记录才勾选完成。
- 跨模块 PR 关联同一功能契约，说明拟定契约与实际 OpenAPI 的差异及原因。前端与后端可用各自短期分支并行提交；集成负责人在两者合并前核对契约、测试和共同验收路径。
- 提交前运行受影响的后端测试、OpenAPI 漂移检查、前端生成类型检查与构建；具体命令见 [README 的校验段](../README.md#校验与契约生成) 和 `.github/workflows/ci.yml`。跨服务或迁移的改动须检查失败、并发与恢复路径。
- GitHub 仓库已建立；合并流程可使用短期分支和 PR 让相关边界的维护者审阅，等 CI 实际通过再合并。当前 CI 配置不证明每次远端运行已成功，也尚未配置 CODEOWNERS 或分支保护；将来明确维护者与权限后再启用这些规则。

外部依据及本项目的取舍见[参考资料](references.md)。本项目采用适合现有代码的最小流程，不引入 KEP、强制 CODEOWNERS 或额外技术栈。
