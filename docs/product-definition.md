# 售后通 · 产品定义 V1

## 1. 定位
面向智能硬件售后的持续服务 Agent。围绕具体服务问题，融合多模态理解、专业知识与 SOP、受控业务动作、真人与 Agent 协同、设备级历史信息和结果核验。

**不是**通用大模型聊天壳、单纯 FAQ RAG、静态流程树，也**不是**人接管后 AI 完全退出的传统转人工。

## 2. 核心业务对象（严禁混淆）

- **Device Passport**：一台设备的长期身份/产品型号/已核验事实/可审计服务经历。不是 Case，也不是用户的聊天记忆。身份未知时不自动创建虚假设备。
- **Service Case**：一次具体问题的服务过程、证据、任务、办理回执、结果和复发/重开记录。可以暂不关联设备，也可以跨越多段会话。
- **Conversation**：客户、AI、真人的消息交流；与 Case 并非强制一对一。
- **Service Task**：某个 Case 下可被委派给真人、Agent 或系统的工作；其审批/执行状态独立。
- **Agent Run**：一次智能执行尝试，与业务状态分离。

## 3. 人机协作

用户只需一个连续的服务入口。真人加入时已有对话、证据、Case 摘要可由其授权阅读，不重复询问基础事实。

- `AI_LEAD`：AI 可按权限直接对外答复。
- `CO_SERVICE`：AI 与真人同时工作；默认人工控制公开回复，AI 继续查知识、整理证据、提出草稿；明确授权时允许 AI 发布。
- `HUMAN_LEAD`：真人主导回复，AI 做内部 Copilot 工作，不直接外发。

**注意**：对外发言权、服务工作责任、售后操作审批是三个不同维度。三种模式是协作策略，不等于谁有退款/售后办理权限。

## 4. 用户旅程

1. 用户提出问题，上传照片/描述；系统快速接收并确认。
2. Agent 读取已授权的相关设备事实、当前 Case 和必要的历史信息。
3. Agent 按需调用知识工具与经过版本管理的 SOP/Skills，追问或引导安全排查。
4. 如需人工，产生协作任务，客服看到经过整理的事实与待决定问题。
5. 人与 Agent 可同时执行**不同**任务，业务动作经授权后执行，保存外部回执。
6. 核验处理结果；问题未解决时继续服务；客户同意后可创建后续跟进任务。

## 5. Web 页面

- `/support`：用户聊天、附件、可操作的排查卡、AI / 人工角色标识、真实执行进度、服务结果。
- `/desk`：客服收件箱、会话、Case 摘要、当前证据、Agent 任务与草稿、审批、发言控制。
- `/devices/:id`：设备资料、已核实事实与历史服务记录（按角色过滤）。

初版保持单一 Web 应用中的两个角色视图，不提前拆成两个独立的前端产品。

## 6. 用户体验与性能目标（非已测数据）

- 前端点击反馈开始：200 ms 内；用户消息本地呈现、由服务器确认再更新状态。
- 文本消息受理 API：P95 < 500 ms（不包括文件上传/模型处理）。
- Agent 首个**真实**进度或内容：争取 P95 <= 2 秒；不能把假进度当完成。
- 人工切换状态通知：争取 P95 <= 1 秒；实时订阅失败时能重新查询/恢复。
- 流式输出、上下文按需加载、模型与工具分时延追踪；隐藏不适合用户看到的原始推理或内部工具信息。
- 故障/断线后原消息与执行记录不丢、不重复请求售后动作。

## 7. 第一条完整业务纵切面

用户报障 →（可选设备档案）→ Agent 检索知识 / 指导排查 → 人工加入（CO_SERVICE）→ Agent 做内部资料整理 → 具有权限的人批准一次**模拟**售后动作 → 记录真实模拟回执 → 结果核验。

不得把模拟操作宣传为已经调用真实 Anker 售后系统。对于危险的硬件异常，必须将安全建议置于一般故障排查之前。

## 8. 非目标（第一阶段）

不建设通用 CRM SaaS、多租户计费、复杂多 Agent 群聊、通用 Skill 商店、大规模知识索引集群，也不绑定商业 Jev 服务。

## 9. Agentic Interface / Generative UI 设计

### 9.1 产品定位

本项目适合引入 Generative UI，但它是现有 `/support`、`/desk` 和设备页中的**受控动态交互层**，不是新的产品入口，也不是对传统页面的替代：

- 固定导航、会话、Case/设备详情、账号与可访问性框架继续由前端代码维护。
- Agent 只根据当前角色、Service Case 状态、已授权上下文和 Skill 输出一个声明式、版本化的 UI Schema；前端只渲染组件目录中已实现的组件。
- 不允许模型生成或执行 HTML、JavaScript、CSS、SQL、任意 URL 或前端事件处理代码。
- UI Schema 是可失效的交互投影，不是 Device Passport、Service Case、Conversation、Service Task、Agent Run 或业务回执的事实来源。
- 无法生成、校验失败或客户端不支持时，退回普通消息和固定表单，核心售后流程仍可完成。

这一模式尤其适合售后，因为每轮最合适的输入与操作会随问题、证据缺口、风险、处理阶段和协作模式变化；但页面框架、权限和业务规则必须保持确定性。

### 9.2 用户侧模式

用户侧目标是减少反复描述，并让当前任务、风险和等待原因清楚可见。

| Case 情境 | 动态组件 | 用户交互 | 业务结果边界 |
|---|---|---|---|
| 设备身份不足 | 单选/搜索问题卡、型号标签拍摄卡 | 选择型号或上传标签图片 | 只形成用户陈述或候选 Evidence，不自动创建已核验设备事实 |
| 视觉证据不足 | 图片上传卡、拍摄指引 | 上传端口、线材或异常部位图片 | 文件先经上传安全校验；模型观察仍需标注来源和可信状态 |
| 低风险排查 | 诊断步骤卡、逐项结果按钮 | 标记“完成/未解决/无法执行” | 记录步骤反馈，不把“完成步骤”当“问题已解决” |
| 等待结果核验 | 核验表单、延迟观察卡 | 填写指示灯、电量前后值和观察时间 | 只有后端验证器满足冻结条件才可解决 Case |
| 安全风险或能力不足 | 风险提示、停止操作、人工协助卡 | 确认停止测试或请求人工 | 安全提示优先；人工交接不等于 Case 已解决 |
| 已提交动作 | 回执/进度卡 | 查看处理中、成功、失败或未知 | 状态来自真实 Service Task/ActionRecord/回执，不由 Agent 文案推断 |

每张交互卡应说明“为什么现在问、会用于什么、是否必填、失败出口是什么”。一次只呈现少量高价值输入，并保留文本入口，避免把未知场景强塞进固定问卷。

### 9.3 客服侧模式

客服侧目标是减少信息搜寻和重复整理，但不替代客服判断。`/desk` 可按当前 Case 生成：

- **Case 摘要卡**：问题、当前状态、等待对象、关联 Conversation/Device；每项事实带来源与核验状态。
- **证据与诊断卡**：已确认、候选、冲突、缺失信息分栏；诊断假设必须引用 Evidence。
- **风险提示卡**：安全风险、政策边界、过期数据和权限变化，优先级高于一般建议。
- **推荐 Skill 卡**：说明适用原因、所需证据、风险级别和失败出口；“推荐/已加载”不显示为“已完成”。
- **下一步操作卡**：创建任务、请求补充证据、审核草稿、批准/拒绝动作、切换协作模式；按钮只提交意图。
- **服务流程图**：从真实 Case/Task/Action 状态投影已完成、进行中、等待与失败节点，不让模型虚构完成进度。

在 `CO_SERVICE` 和 `HUMAN_LEAD` 下，Agent 可继续生成 INTERNAL 组件与草稿；只有后端按最新 `reply_policy` 授权的内容才能进入用户可见界面。

### 9.4 与核心模块的关系

- **Service Case**：是 UI 编排的主要业务上下文，提供问题、状态、版本、证据缺口、任务、动作与等待原因。一次 UI 可以引用多个关联 Conversation，但不得把 Conversation 当成 Case。
- **Device Passport**：只提供当前 Case 已授权且相关的设备身份与 VERIFIED facts；候选事实必须显式标记，不能以确定口吻渲染。
- **Skill / Capability**：定义可用的交互意图、所需输入、输出结构、风险、成功标准和失败出口，影响 Agent 可选择的组件组合；Skill 不携带可执行前端代码，也不能扩大工具权限。
- **Agent Runtime**：先由 Context Builder 构建最小授权上下文，再由 Resolver/Rule 过滤可用 Skill、组件和动作；Agent 决定是否需要 UI 及组件组合，服务端校验后发布。
- **Frontend Renderer**：维护版本化组件目录，校验 Schema，绑定可访问性与设计系统，发送带幂等键和期望版本的动作意图；不解释 Prompt、不执行业务规则。

### 9.5 产品原则与上线门槛

1. **先文本、后增强**：没有动态 UI 也能理解进度并继续服务；重要结果同时有简洁文本说明。
2. **证据可见**：事实、用户陈述、模型假设和模拟结果采用不同标签，不用视觉确定性掩盖数据不确定性。
3. **高影响动作显式确认**：不可逆、费用、隐私、保修/退款承诺和外部系统动作不使用模糊的一键按钮。
4. **过期即失效**：Case、Conversation、审批或权限版本变化后，旧卡不可继续提交，应刷新为最新状态。
5. **真实进度**：只展示持久事件、任务状态和真实回执；模型正在思考、工具加载或前端动画不能表示业务已完成。
6. **少而稳定的组件目录**：V1 只支持信息、证据、步骤、风险、确认、上传、进度、Skill 推荐和流程等售后组件，不建设通用页面生成器。

当前已实现受控 UI Schema、组件目录、React Renderer 和低风险 UI 动作 API；本节描述的完整组件纵切面仍是产品目标。实际完成状态与待验范围以[开发计划](development-plan.md)和阶段验收记录为准。

### 9.6 可借鉴的成熟模式

- ChatGPT 类产品：仅在结构化信息需要查看、比较、编辑或确认时嵌入组件；组件失败不阻断对话，临时 UI 状态不充当业务存储。
- Copilot / Adaptive Cards：用版本化 JSON 卡片适配宿主设计系统；每次提交带唯一动作标识，避免用户操作旧卡或连续卡时混淆。
- Vercel AI SDK：将类型化工具调用/结果映射到已编写组件，并明确输入中、结果可用、失败等状态；本项目借鉴状态模型，不引入其框架依赖。
- A2UI：借鉴声明式数据、受信组件 Catalog、结构与数据分离、增量更新；因协议仍在演进，V1 先定义 ServiceOS 自有最小协议，不直接绑定外部标准。
