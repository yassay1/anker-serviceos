# Agent 受限动作演示脚本

## 演示目标

展示 Agent 如何查阅官方赛题提供的脱敏订单样例、提交一条待审批的售后动作申请，再由主管和 Mock Worker 完成后续流程。演示证明的是 ServiceOS 中的协作、权限、审计和状态流转，不证明已经连接 Anker 的订单或售后系统。

## 场景与数据边界

- 选用官方赛题 Excel 的客诉行 `Anker001`：客户表示只收到配件包、未收到主机，并询问订单是否发货及下一步处理。
- 订单行包含两个运单号、两个发货日期和两个妥投状态。运行时查询按源表列出顺序逐包裹呈现。
- 源表把承运商写成合并文本，不能可靠映射到单个包裹；演示不做这种归属，也不推断某个包裹装有主机或配件。
- 这些信息是脱敏静态参考资料，不是当前订单状态或 Anker 已核验售后政策。演示时不要显示不必要的地址或把物流结果描述成实时查询。

## 演示角色

| 角色 | 操作 |
|---|---|
| 客户 | 描述缺件，并在需要时明确提出补寄申请；查看 Mock 回执并提交结果核验 |
| Agent | 查询只读参考资料；客户明确提出处理请求后，用受限 Tool 创建待审批动作 |
| 客服主管 | 查看同一 Case 和客户对话，批准或拒绝申请 |
| Mock Action Worker | 仅领取主管批准的动作，写入明确标为 Mock 的回执 |

主管是审批决策人。Agent 不替代主管，也不能通过 Prompt 绕过 Case 状态、服务权限或 Worker 的审批门槛。

## 主链路演示

1. 以客户身份在 `/support` 描述：“订单 Anker001 只收到配件包，主机没收到。请帮我确认发货情况。”
2. Agent 使用订单查询 Tool。展示两个包裹各自的运单号、发货日和源记录中的妥投文字，并说明这是静态样例；仅凭该表无法确认包裹内商品或实时承运商结果。
3. Agent 询问客户是否希望提出补寄申请，不把咨询本身当成客户同意补寄。
4. 客户明确回复：“我确认只收到配件包，请帮我申请补寄主机。”Agent 调用 `request_mock_service_action`，只提交 `RESHIP` 和申请理由。服务端从 AgentRun 和会话关联中确定租户、客户、Case、版本及幂等标识。
5. 切换到不同的主管账号，在 `/cases` 检查对话、静态订单依据和申请。此时 CaseAction 应为 `WAITING_APPROVAL`、适配器为 `MOCK`，尚无执行回执。
6. 先展示拒绝分支：主管可因静态资料不足以核实缺件而拒绝；拒绝后 Worker 不执行，不产生回执。
7. 如需展示成功回执和客户核验，可在隔离的开发/测试演示 Case 中明确将其作为流程演练，由主管批准 Mock 申请。Worker 返回 `MOCK-...` 回执后，客户再提交核验；只有核验通过，Case 才会解决。

第 7 步是受控 Mock 流程演练，不表示对 `Anker001` 真实补寄申请的业务判断，也不连接真实售后系统。若现场只有一个 Case，建议按第 6 步收尾；另用专门的培训 Case 演示成功执行分支。

## 现场验收观察点

- Agent 的订单查询结果带 `REFERENCE_ORDER` 来源边界和结构化 `shipments`；不暴露未使用的客户地址。
- Agent 请求只在开发/测试环境有效；模型不能传入 tenant、customer、Case ID、Case 版本或审批人。
- 一个 AgentRun 的重复调用返回同一动作；改写同一请求不会创建第二条动作。
- 支持人员不能审批；主管不能批准自己以客服身份提交的申请；Agent 申请必须由主管决策。
- 拒绝时无 Worker 执行；批准后 Worker 回执明确标记 `MOCK`；Mock 成功回执本身不会自动解决 Case。
- Case 只能在客户结果核验通过后解决；演示结束时明确指出没有真实 Anker API 调用。
