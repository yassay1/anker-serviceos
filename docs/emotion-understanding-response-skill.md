# 用户表达理解与回应 Skill 设计计划

> 状态：首批四步的轻量实现已完成；领域人工评测尚未开始。当前能力是短语触发的提示引导，不是经售后数据验证的情绪分类器，也不改变现有 API、权限、协作策略或业务状态机。

## 目标与原则

让 Agent 对用户当前消息中明确表达的服务感受作出适度回应：不满时先回应具体问题，困惑时分步骤解释，着急时说明已确认状态和下一步；证据不足时使用中性措辞。该能力帮助生成更合适的回复，不用于判断用户心理、设备事实、Case 状态、风险等级或工具权限。

遵守以下约束：

- Device Passport 与 Service Case 的业务事实仍以现有应用服务和核验流程为准。用户情绪或 Agent 推断不能成为已核验事实。
- 情绪线索不能改变 `AI_LEAD` / `CO_SERVICE` / `HUMAN_LEAD`、回复策略、审批条件或工具授权。公开回复继续由 `ConversationService` 校验和发布。
- 不新增分类器、数据库表、持久化情绪字段、Checkpointer 字段或第三方依赖；不输出或保存原始思维链。
- 情绪判断默认只针对当前一轮可见的用户表达，不形成长期客户画像。

## 当前代码基线

- `backend/serviceos_api/application/skills.py` 定义粗粒度 `ServiceExpressionSignal` 契约和 `emotion-assessment` 注册项；注册项仍为 `PREPARED`，没有结构化情绪结果生产者。
- `application/agent_services.py` 构建授权上下文、筛选可用 Skill，并提供 `load_skill` 服务；情绪契约没有进入可调用 Skill 列表。
- `agents/runtime.py` 使用 LangChain `create_agent`，设置短的常驻回复规则并注册既有 `load_skill` 工具。对当前用户文本做低成本短语匹配后，应用层可在本次模型调用的 system prompt 中附加详细指导；没有新的模型或 Skill 工具调用。
- `agents/result.py` 约束 Agent 结果；Worker 负责运行与结果持久化；用户可见消息仍通过 Conversation 服务发布，并复核当前协作模式和回复策略。
- 当前会话历史来自已授权的公开消息上下文。LangGraph Checkpoint 是运行恢复数据，不是业务事实库，也不应被用作长期情绪记忆。

动态指导文本只作为本次模型调用的 system prompt；应用层短语命中结果不写入业务数据库、AgentRun 结果或日志，也不添加消息/工具调用，因此没有新增情绪判断的 Checkpoint 消息记录。普通诊断 Skill 仍按原规则记录。Agent 结构化结果与公开回复均不包含情绪标签。

## 首批四步计划

### 第一步：定义最小服务感受信号

**目标**：只描述对当前服务互动有用、且能从用户表达支持的线索。

建议内部表示保持很小：

| 字段 | 建议取值 | 用途与限制 |
|---|---|---|
| `valence` | `negative` / `neutral` / `positive` / `unclear` | 粗略表达当前服务感受；不代表用户稳定性格或真实心理状态 |
| `cue` | `frustration` / `confusion` / `concern` / `gratitude` / `none` / `unclear` | 可选的回应线索；一轮最多选一个主要线索，证据不够则 `unclear` |
| `evidence` | `explicit` / `suggested` / `insufficient` | 描述判断依据强弱，不伪装成经校准的概率置信度 |
| `source_message_id` | 当前可见消息标识（如运行上下文可用） | 便于内部追踪依据；不得把用户原话复制进持久化情绪记录 |

不在首版增加数值情绪分、愤怒等级、心理状态、人格标签或解释性长文本。紧急程度与情绪是不同维度；首版不从情绪推导紧急度。显式出现的安全/危急事实继续由既有业务规则处理。

**已实现**：`application/skills.py` 的预备 `ServiceExpressionSignal` 契约使用上述有限字段。当前运行时尚不产生该结构化对象；模型只按提示对用户明确表达做临时语言适配，不返回标签。没有新增 API 或持久化字段。

**验收条件**：表示有限、可选且可不判断；对反讽、简短回复、转述、服务对象以外的情绪表达允许 `unclear`；信号不被映射为权限、风险或业务状态。

### 第二步：实现最小回应指导，并限制按需注入

**目标**：用现有模型调用完成“理解当前表达并调整回复”，不增加单独情绪分类模型调用。

运行时采用短的常驻基线和应用层短语门控：只有当前消息命中少量明确不满、困惑、担忧或着急表达时，才把详细回应指导附加到 system prompt。门控仅决定是否提供写作指导，不等于情绪分类；短语表会漏掉隐含表达，也可能因引用或否定而误触发。未命中时使用常驻中性基线。未用 `load_skill` 工具注入，因为其调用消息会进入持久 Checkpoint。

回应指导包含：只看当前消息中可观察的表达；避免读心和给用户贴标签；据具体问题回应；提供可确认的下一步；证据不足时使用中性语气。它是提示指导，不是情绪分类器/API，也不能自行调用新增工具。结构化契约 `emotion-assessment` 保持 `PREPARED`，并非本轮可调用 Skill。

**已实现**：`agents/runtime.py` 加入短常驻规则；`application/skills.py` 提供短语匹配和固定回应指导。未调用 `load_skill`，没有额外模型调用、工具调用或数据库查询；命中表达的轮次会增加少量 system prompt Token，其他轮次只有短基线。

**验收条件**：未触发时仍有尊重、中性的安全退化；提示注入不改变工具集合；普通服务轮次不增加模型调用或工具调用；Agent 的完整流程继续使用既有 Worker、Agent Loop 和响应发布链路。

### 第三步：限定情绪线索对回复和人工接续的影响

**目标**：只允许改变语言风格、信息密度和解释顺序，不改变事实、流程或操作权限。

建议的回应策略：

- **明确不满**：先承认用户指出的具体问题或等待/重复沟通成本，再说明当前能做的下一步；避免泛化道歉或保证结果。
- **困惑**：一次解释一个关键点，使用短步骤；先确认用户卡住的环节，避免重复堆叠术语。
- **担忧**：先区分已确认信息和待核验信息，再解释如何核实；不以安抚为由把候选设备事实说成 VERIFIED。
- **着急**：优先给出当前状态和下一步；没有服务端依据时不承诺具体时限。情绪本身不代表业务紧急等级。
- **感谢/正向表达**：简短回应并回到服务目标，不额外推断满意或结案。
- **不明确**：使用自然、中性的表达；不说“我知道你很生气/担心”。

情绪线索可以让 Agent 在答案中建议使用现有客服协助入口，但不能自动创建客服任务、切换协作模式、绕过审批、调用敏感操作或改变对外发布资格。当前 Agent Runtime 未注册人工接续工具，因此对明确人工请求不能声称已转接或已创建任务；最终发布资格仍由 Conversation 服务决定。

**验收条件**：回复中的情绪承认要能指向用户明确表达或具体服务事件；不确定判断不被写成用户事实；所有公开输出仍由 `ConversationService` 复核；任何业务写入仍经现有应用服务和类型化命令。

### 第四步：限定时效与数据生命周期

**目标**：把情绪作为短期、可更新的服务信号，尽量不产生新数据面。

首版只从当前请求已授权的用户消息中临时推断，随本轮回复结束即失效；不跨会话读取、不写入 Device Passport、Service Case、长期记忆、普通会话消息或数据库字段。无需为该信号创建 Checkpoint 状态；已有 Checkpoint 仅继续承担 Agent 恢复职责。常规 AgentRun、工具审计和消息持久化按现有职责运行，不复制情绪标签或推断依据到其中。

如果未来确有客服查看短期趋势的业务需求，另行评审独立字段/事件、用途、来源、访问控制、保留期限、删除机制和用户告知；不得将临时判断默认为永久客户标签。原始用户消息按既有消息保留策略管理，不为情绪功能延长保存期。

**验收条件**：数据库模型与迁移、公开 API/OpenAPI、会话消息结构和业务状态机均无新增情绪持久化；日志、错误信息和内部 UI 不泄漏原始思维链或不必要的客户原话。

## 实施前验收门槛

人工评测仍是后续门槛。中文售后样例应覆盖明确不满、困惑、担忧、着急、感谢、中性、反讽、转述与证据不足；评估短语门控漏触发、误触发、错误承诺时限、无依据承认用户感受等不同成本。不能只依据总体准确率或模型自评决定上线。上线范围与评测门槛须在独立任务中确定。

本次已新增单元回归覆盖粗粒度契约字段、拒绝额外推理/授权字段、短语门控命中与中性退化。发布前仍须验证真实模型下的动态提示是否改善回复、隐含表达漏触发和否定/引用误触发的成本、工具权限和审批边界、VERIFIED 事实保护、人工接续与公开发布规则；本次未做真实 Provider 评测。

## 明确不在本计划范围内

- 外部情绪分析 API、通用文本分类依赖或领域模型训练。
- 情绪/心理画像、跨会话趋势、情绪驱动的 SLA/风险评分或自动路由。
- 修改 Case、Device Passport、审批规则、协作模式、消息 API、SSE、Generative UI 或持久化契约。
- 自动人工接管、自动补偿、退款/换机等敏感动作。
